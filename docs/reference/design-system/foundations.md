# Design System — Foundations

## 2. Foundations

### 2.1 Color

Color is sourced from the Material 3 expressive scheme; this section defines the *roles* those tokens play in this app.

- **Primary.** The accent. Used for emphasis on text and chrome (eyebrows, key stats, the leading mark of a section, progress indicators, cursors, active toggle states, a button's filled style), and — deliberately — as the **surface fill of a hero stat card**: the page-opening stat tile (e.g. the profile screen's pages-read hero). At most one primary-filled card per scrollable region. Inside such a card the content colour is `onPrimary`; demoted text drops to `onPrimary` at ~0.75 alpha; the divider drops to `onPrimary` at ~0.25 alpha; if the card needs a call-to-action it steps down a tier (elevated or tonal) so it doesn't disappear into the surface. This treatment is reserved for stat heroes — cards built around imagery (covers, photos) keep a `surfaceContainer*` shade so the imagery, not the chrome, carries the colour. Beyond the stat hero, primary is **not** a background colour — ordinary cards, tiles, sections, and grouped regions use page background or a `surfaceContainer*` shade.
- **On-surface / on-background.** Body and headline copy. Default for almost all readable type.
- **On-surface-variant.** Demoted copy: suffixes, captions, secondary metadata, inactive labels. Use to push information back without losing legibility.
- **Surface / background.** Page canvas. Plain.
- **Surface-container, surface-container-high, surface-container-highest.** Elevated tiles, cards, and grouped sections. Step up the container shade to express grouping or focus, not depth in pixels — elevation is communicated by tone, not by drop shadows.
- **Surface-container-lowest.** Reserved for modal sheets and overlays that sit *above* the page rather than within it.
- **Outline / outline-variant.** Hairline dividers and the rare bordered control. Avoid dense rule lines; prefer whitespace and tone changes.
- **Inverse-primary.** Notification dots and small attention markers on chrome.
- **Error / on-error.** Destructive and validation states only.
- **Rating gold (`RatingGold`).** A single warm gold reserved exclusively for rating-star glyphs — both the read-only community/review rating and the interactive personal rating control. It sits *outside* the Material scheme (and the dynamic-color override) because the gold reads identically in light and dark and is a deliberate "rating" signal rather than a theme role. Never use it for anything that isn't a rating star, and never re-declare the hex at a call site.
- **Mood-ink and monogram-cover fixed inks.** Two more fixed-ink families sit outside the Material scheme for the same reason as `RatingGold` — they read identically in light and dark by design, as a printed-jacket ink rather than a theme role. `MoodInkCosyBackground`/`MoodInkCosyForeground`, `MoodInkDreadBackground`/`MoodInkDreadForeground`/`MoodInkDreadEyebrow`, and `MoodInkHeartWrenchBackground`/`MoodInkHeartWrenchForeground` tint three of Explore's four "Browse by mood" tiles (the fourth stays on ordinary theme roles — `surfaceContainerHigh`/`onSurface`/`primary`/`onSurfaceVariant` — so the grid keeps one tonal breather among the three inked tiles). `MonogramCoverInk`/`MonogramCoverForeground` back the **app-wide coverless-cover fallback** (the "Coverless title cover" component, §4) — keyed purely on "no cover art resolves," never on a book's release status, so a real jacket always wins over the monogram regardless of whether the title is out yet. `ReadingHeroBackdropForeground` is a narrower, single-purpose fixed ink: the Reading screen's featured-hero card backdrop (§5 "Reading featured-hero card") is a theme-role treatment (a black scrim + a fade into the card's own `surfaceContainerLow`, not a fixed-ink field), but every line of text painted directly over that backdrop — series eyebrow, hero title, byline, "Your pace", the page-count/percentage stat, and the deadline row — still needs a colour that reads reliably against an arbitrary blurred cover image regardless of theme, so the *text* colour is fixed across the whole card, not only its top band. All live next to `RatingGold` in `core/designsystem`'s `Color.kt`; never re-declare one of these hexes at a call site.
- **Spoiler redaction (`ColorScheme.spoilerEditorHighlight` / `ColorScheme.spoilerCover`).** The treatment for inline spoiler runs inside a review, both derived from `onSurfaceVariant` so they track light/dark. The two roles are deliberately different by surface: in the **review editor** a spoiler run gets the translucent `spoilerEditorHighlight` wash (the author must keep reading their own words), while on **display** the run is hidden under the near-solid `spoilerCover` block until the reader taps to reveal it. Use these only for the per-run spoiler mark; the whole-review spoiler gate is a separate "Show spoiler" affordance (§5), not a colour role.

Dynamic color (Android 12+ Material You) is supported but **off by default**. The editorial scheme is the canonical look; dynamic color is an opt-in personalisation, not the design.

### 2.2 Typography

Two type families carry the system, split by voice. Both are bundled with the app (as Compose Multiplatform font resources) so the branded type renders identically on every platform — Android, iOS, and desktop:

- **Fraunces** — the editorial serif. A serif face with true italics; carries every role where the editorial voice should be heard: page titles, display headlines, italic headlines, italic body prose, hero stats, and the decorative quote glyph. Stats use Fraunces with tabular figures so digits don't jitter when numbers animate.
- **Inter** — the chrome sans. Carries everything that should retreat: eyebrows (all-caps with wide tracking), card and list titles, Material component internals (top-bar titles, button labels, navigation labels, dropdown items), and any utility label. Inter is roman in this system; if a chrome surface needs italic, that is a sign the role belongs in the editorial scale instead.

Two parallel scales coexist:

- **Material typography** — the standard body/title/label scale used inside off-the-shelf Material 3 components. Components consume this implicitly; do not override it for component internals.
- **Editorial typography** — a project-specific scale, accessed alongside Material typography, used for any text the *screen itself* composes. Roles below.

| Role            | Where it goes                                                                 | Character                          |
| --------------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| `eyebrow`       | All-caps section labels, kicker over a headline, accent over a hero stat     | Wide letter-spacing, semibold      |
| `eyebrowSmall`  | Same role, when packed inside cards/rows                                     | As above, tighter                  |
| `pageTitle`     | The screen's primary title rendered *inside* the scrolling page (not the top-bar slot — that uses Material `titleLarge`). Reach for it on root screens whose top bar is transparent or absent. | Roman, semibold, large |
| `display`       | Section headlines that follow an eyebrow                                     | Italic, semibold, expressive       |
| `headlineMedium` / `headlineSmall` | Subsection or modal headlines                                  | Italic, semibold                   |
| `titleLarge` / `titleMedium` / `titleSmall` | Card titles, list item titles, grouped row headers       | Roman, semibold                    |
| `bodyLarge` / `body` / `bodySmall` | Running prose, descriptions, captions                            | Italic                             |
| `statHero`      | The single largest number on a screen (e.g. a hero count)                    | Italic, semibold, oversize         |
| `statLarge`     | Editable hero numbers (input fields styled as stats)                          | Italic, semibold                   |
| `quoteGlyph`    | Decorative oversized quotation mark — used either behind an actual quote block or as an editorial flourish in an empty state. Tinted `onSurfaceVariant` at low alpha. | Display face, very large, low alpha |

**`quoteGlyph` tint exception.** The create-list sheet's quote rule (§5 "Title-page sheet") tints the glyph `primary` at 0.28 alpha instead of `onSurfaceVariant`. There the glyph sits *on* a hairline divider as a wayfinding mark — a small piece of chrome breaking a rule line, not a decorative wash behind prose — so it reads correctly in the accent colour rather than the muted one. Pick the tint by which job the glyph is doing in a given surface: `onSurfaceVariant` behind an actual quote or empty-state flourish (the default), `primary` when it interrupts a rule line as this pattern does.

**Mood tile title exception.** Explore's "Browse by mood" tile title (§4 "Browse-by-mood grid") sizes `headlineSmall` down via `.copy(fontSize = 19.sp, lineHeight = 22.sp)` rather than using it at its full 24sp. The mood API returns single, often long, unbroken words ("adventurous", "mysterious") that a half-grid tile (~140dp) can't set at the full headline size without forcing a mid-word break — there's no space to wrap on until the glyphs themselves shrink. 19/22 is the spec's own literal type role for this title, sitting between `headlineSmall` and `titleLarge` in the scale, so it doesn't earn a new named `EditorialTypography` field for one surface. Paired with `Hyphens.None` + `LineBreak.Heading` (the same mid-word-break guard `CoverlessTitleCover` uses) and a 2-line cap.

Italic is a deliberate signal of editorial voice; it is reserved for display, headlines, body prose, and stats. Roman is reserved for page titles, card/list titles, and component chrome — places where italic would feel decorative rather than deliberate.

Never inline an ad-hoc `TextStyle`; pick the closest editorial or Material role and `.copy(...)` only when a documented exception requires it (e.g. tinting `quoteGlyph` with a low alpha).

### 2.3 Shape & elevation

- **Corners.** Small radii on cards and tiles; medium on buttons (Material defaults via expressive theme); larger, fully-rounded for the active state of toggle buttons. Cover art uses a subtle radius to hint at a printed object without softening it into a sticker.
- **Elevation.** Tonal, not shadowed. Surface-container shades replace drop shadows for grouping. The one exception is book covers, which carry a slight shadow to read as physical objects on the page.
- **Accent bar.** A short, primary-coloured bar in two sizes, picked by the role of the eyebrow it leads:
  - **Section bar — 32×4 dp.** The "this is a section / this is a sheet" mark. Sits in the page gutter (not inside a card) and precedes a full-size `eyebrow` + display/headline pair. Used by sheet headers, settings section headers, and any top-level region introduction.
  - **Inline bar — 20×1 dp hairline.** The smaller-scale variant for an eyebrow living *inside* a card, hero region, or subcomponent. Always paired with `eyebrowSmall`, never with the full `eyebrow`. Used on featured cards (Reading), page-title accents (Library), inline status callouts (Book detail), and the Book-detail shelve control's "Shelve this book" opener. A third register carries **no bar at all** — a compact in-flow label (still `eyebrowSmall`, `onSurfaceVariant`) for a sub-label that sits inside a section the page has already introduced, rather than opening a new one: Book detail's `YOUR RATING` / `YOUR TAGS` / `YOUR REVIEW` / `TAGS` / `FIND IT` labels are this register. Never mix: a region-opening label gets a bar (32×4 full or 20×1 inline), an in-flow sub-label gets none.
  Never mix sizes: a full `eyebrow` always gets the 32×4 bar; an `eyebrowSmall` gets either the 20×1 hairline or no bar at all. The create-list sheet's **title-page composition** (§5) is the one documented exception: its full `eyebrow` carries no bar at all, because the quote-glyph-broken hairline rule beneath it (§5) already plays the "this is a region opening" role the bar exists to signal. Do not read this as license for a second bar-less full eyebrow elsewhere without updating this doc.

### 2.4 Spacing

Spacing is rhythmic, not formulaic. The recurring values are:

- **4 / 8** dp — tight inline gaps (icon-to-label, badge offsets).
- **12 / 16** dp — within-component padding, label-to-control gaps.
- **20 / 24** dp — page horizontal padding, gap between a card's image and its text block.
- **28 / 32** dp — gap between distinct content blocks inside a sheet or hero region.
- **40 / 48** dp — gap between major page sections.

Sections always breathe. Two adjacent eyebrow/headline pairs without a generous gap between them is a layout bug.

### 2.5 Motion

- Use the Material **expressive** motion scheme; do not hand-author durations or easings unless animating a custom property the scheme cannot express.
- **Press feedback.** Tappable cards, primary (filled) buttons, and ripple-less hero surfaces scale to ~0.97 while pressed and ease back to 1f on release. The scale rides an `InteractionSource` so it lines up with the platform's pressed-state ticks; it is wired through `Modifier.pressScale` (a press-driven `graphicsLayer` scale) or its `Modifier.pressScaleClickable` convenience (which bundles a ripple-less `clickable`). Suppressed under reduced motion (§2.5 gate). Press scale is the *only* indication on ripple-less surfaces — never strip the ripple from a card or hero without adding the scale, or the surface loses its press feedback entirely. Tonal/outlined/text/elevated buttons keep the Material ripple + pressed-shape morph and do not stack scale on top; a single button surface only carries one press treatment.
- **Press haptics.** A *commit* haptic fires only on commit-class actions (mark-as-read, save, confirm) — never on navigation taps (tapping a book card to open detail, tapping a row to push a sub-page). Press scale is purely visual; it never implies a haptic.
- **Desktop hover & cursor.** Pointer-only affordances that are inert on touch (no pointer device) and surface on desktop, where the bespoke `jvmMain` screen layouts apply them. Two shared modifiers carry them: `Modifier.pointerHandCursor()` puts the platform "clickable" hand cursor on a surface while the pointer is over it; `Modifier.hoverHighlight(interactionSource, shape, color)` cross-fades a subtle overlay (default: a low-alpha `onSurface` wash) over a surface while hovered — the hover sibling of `pressScale`, sharing the same `InteractionSource` as the surface's `clickable`/`hoverable`. Reach for hover highlight on rows, cards, and list/grid cells that a desktop user would expect to light up under the pointer; pair it with the hand cursor on the same surface. Do not author bespoke hover tints or cursor swaps per screen — these two modifiers are the only way to wire desktop hover affordances. They are decorative-only (never the sole indication of state) and carry no haptic.
- **Desktop tooltip.** Icon-only controls (back, close, refresh, scan, overflow, the Library masthead control line's Select circle, the selection header's exit/trash circles, the session peek bar's transport buttons) carry only a `contentDescription` — invisible to a sighted pointer user, so the hover state promises a label that never arrives. The shared `DesktopTooltip(text) { control }` wraps such a control in a hover tooltip: on desktop it renders a small editorial surface (`surfaceContainerHighest`, 8dp radius, Inter `labelMedium`) after a short hover delay; on touch it is a **pure pass-through** (no wrapping layout node), so a shared composable wrapped in it is byte-identical on Android and iOS. It is a `commonMain` expect (`:core:designsystem`) with a jvm `actual` (Compose Desktop's hover-triggered `TooltipArea`, *not* Material3's long-press `TooltipBox`) and a mobile pass-through `actual` — the same seam shape as `pointerHandCursor()`. Pass the human-readable label as `text` (the icon's `contentDescription` stays the accessibility label); it is decorative-only and carries no haptic. Reach for it on every icon-only desktop control — including ones living in shared `commonMain` components — and never hand-roll a per-screen tooltip. Controls that already show a text label (a `RhaydusButton`, a labelled sidebar row) do not get one.
- **Desktop scrollbar.** Long desktop lists and grids carry a persistent vertical scrollbar — mouse-wheel scrolling has no fling or edge-glow, so the scrollbar is how a desktop user reads and grabs their position. The `DesktopVerticalScrollbar(gridState, modifier)` (jvm-only, foundation `designsystem-core` — `nl.rhaydus.designsystem.component.DesktopVerticalScrollbar`) wraps Compose Desktop's `VerticalScrollbar` + `rememberScrollbarAdapter`; overlay it on the trailing edge of the grid's `Box`, driven by the same `LazyGridState` the grid scrolls on. A `LazyListState` overload covers uniform-height `LazyColumn` shelves; a `ScrollState` overload covers non-lazy `verticalScroll` content. Prefer the `ScrollState` overload when the content is short and its items vary wildly in height (e.g. the desktop Reading list, where a tall featured card sits above short rows): a lazy adapter only *estimates* total height from the average measured-item size, so the thumb jumps as the tall item scrolls out — a fully-measured `ScrollState` reports the exact extent and keeps the thumb stable. The thumb is keyed to the theme's `onSurface` (Compose Desktop's default thumb is near-black and invisible on the dark editorial surfaces), brightening on hover. Touch platforms get no scrollbar (the fling + overscroll glow is the affordance), so it never appears in a `mobileMain` layout. This is the desktop counterpart to — not a contradiction of — the carousel "no scrollbar" rule (§4): book *carousels* still lean on the partially-clipped edge card as their overflow cue; the scrollbar is for the long *vertical* shelves a desktop window makes tall.
- **Desktop back strip.** A pushed desktop screen carries a static `DesktopBackStrip(onNavigateBack, backIcon)` (jvm-only, foundation `designsystem-core`) in place of a scroll-collapsing top bar — a single hand-cursored back `IconButton` in the leading gutter, over the screen's opaque background. The strip is brand-agnostic, so the app passes its own back-arrow as a `RhaydusIconResource` (`drawableIconResource(contentDescription = …, icon = SoftcoverIcon.ArrowBack)`). It is the desktop counterpart to the `SoftcoverTopBar` back affordance a `mobileMain` layout uses; never hand-roll a per-screen back row. Used by the desktop Profile, Create List, and Barcode Scanner layouts. Touch platforms get `SoftcoverTopBar` instead, so it never appears in a `mobileMain` layout.
- **Desktop selection: right-click + modifier-click.** Touch enters multi-select via long-press, which is invisible to a pointer user — so desktop adds the two native pointer gestures. **Right-click** on a book cover/row opens a context menu (`DesktopContextMenu`, §4) — Open, Select / Add-to-selection, and the per-book operations that reuse the bulk pipeline (Mark as read, Add to list…, Remove). **Ctrl/Cmd-click** toggles a cover's selection (entering selection mode if needed) and **Shift-click** range-selects the visible span to the last-clicked anchor, both via `Modifier.platformModifierClick(onCtrlClick, onShiftClick)` (the foundation `designsystem-core` modifier, `nl.rhaydus.designsystem.modifier`) — a jvm interceptor that consumes the press in the pointer Initial pass only when a modifier is held, so a plain click still opens the book and the modifier-click is preempted with no double-fire. Both seams are pure pass-throughs on touch (the long-press path is untouched), so the shared library cells stay byte-identical on Android and iOS. Reach for them on any desktop list/grid that supports selection; the per-book context actions reuse the existing bulk actions targeted at a single book (the action carries an explicit id set) rather than a parallel single-item write path.
- **Desktop Esc-to-dismiss.** Pressing **Esc** closes whatever desktop overlay sits over the page — the baseline desktop reflex. The expanded-width modal panel (`AdaptiveModalSheet`'s `Dialog` form, §3.5) gets this for free: Compose Desktop maps a `Dialog`'s `dismissOnBackPress` to Esc. The in-app surfaces that are *not* a `Dialog`/`Popup` — Focus Mode, the full-screen cover viewer, and Library bulk-select / Rearrange mode — wire it explicitly through the jvm-only `Modifier.dismissOnEscape(enabled, onDismiss)` (`:core:designsystem`): while enabled it takes focus once and catches Esc in the *preview* (tunnelling) phase, so it fires even when a descendant text field holds focus, and it is a no-op (never grabbing focus) when disabled — so it can be gated on a transient mode without disturbing normal focus. It is the desktop sibling of the `mobileMain` `BackHandler`; keep both (Esc on desktop, back on touch). Reach for it on any in-app desktop overlay; do not hand-roll per-screen key handling. Accelerator shortcuts beyond Esc (e.g. ⌘F, ⌘,) and a native menu bar are deliberately out of scope for now.
- **Tap-to-dismiss scrims are pointer-only.** A full-screen "tap empty space to clear focus / dismiss" scrim must be wired with `Modifier.pointerInput { detectTapGestures { … } }`, **never** `Modifier.clickable` / `noRippleClickable`. On desktop a `clickable` also binds **Spacebar/Enter** as activation keys, so a focused text field whose space key bubbles up (it isn't fully consumed) lands on the scrim and clears its own focus mid-typing — every field in the app breaks on the spacebar. `detectTapGestures` reacts to pointer taps only (no key binding, not focusable), preserving tap-to-dismiss on touch and desktop without the side effect, and it keeps a phantom full-screen clickable out of the accessibility tree. Reserve `clickable` for surfaces that genuinely *should* activate on Space/Enter (buttons, rows, cards).
- Progress is shown with the wavy progress indicator — flat bars are reserved for chrome (top-bar scrim) and never carry semantic progress.
- Numeric progress animates between values rather than snapping.
- Sheets enter and dismiss from the bottom; overlays cross-fade.
- **Tab-root swap.** Switching between the four bottom-bar roots plays a 200ms cross-fade with a 12dp upward drift on the incoming tab — never a hard cut, never a horizontal slide (which would imply spatial relation between unrelated roots). Per-tab `rememberSaveable` state survives the swap via a shared `SaveableStateHolder` keyed by tab key. Suppressed under reduced motion (§2.5 gate) — in that case the previous instant swap is used. Sub-screens pushed onto a tab's stack continue to use the standard `ScreenTransition` (currently `None`); this rule applies only to the root-tab swap.
- **Mark-as-read commit choreography.** When a book transitions to the Read shelf via a user action (chip tap on book detail, "Mark as Read" menu item on the reading screen, or progress reaching 100%) the surface plays a ~800–1000ms burst: a primary-color particle burst (`MarkAsReadBurst`, §4), the chip's check-icon punches with a left-to-right reveal, the section-label accent bar pulses, and a single *commit* haptic fires. No other shelf transition (Want-to-read, Reading, DNF) earns the celebration — only Read. On the Reading screen specifically, the celebrated row also performs a "slide to shelf" follow-through: ~320ms downward translate (~96dp) + fade, played before the screen-model action dispatches; the Library bottom-bar icon pulses once in parallel (180ms peak to 1.22× scale, 240ms settle) via the foundation `NavPulse` (`navPulse.pulse(LibraryNavPulseKey)`, observed by the bottom bar through `rememberPulseScale`), so the eye is led from the source row to the shelf where the book just landed. Both the slide and the pulse are suppressed under reduced motion (the action dispatches synchronously instead).
- **Mutation-rejection shake.** When an optimistic mutation rolls back, the affected card/row plays a single horizontal shake: 6dp amplitude, 80ms each half-period, 3 cycles, returning to centre. The card's eyebrow slot also swaps to the error role with a "Couldn't save — tap to retry" label for the duration of the failed state. Use the shared `Modifier.shakeOnError` for this — never hand-roll the animation.
- **Lazy-list add/remove animation.** Only user-triggered list mutations animate; initial load, background refresh, and pagination tail jump as today. Removals fade out and neighbours slide into the vacated space; additions fade in and play a brief 20×1 dp accent-bar pulse (§2.3 inline-bar hairline) at the top edge of the inserted item. The shared `Modifier.mutationAnimated` extension (§4) is the only way to wire this up — do not hand-roll `animateItem` per call site, and never wrap the item in a `Box` to host the modifier (the wrapper layout node causes stale lazy-item measurements).
- **Staggered entry on first composition.** Carousel and list items that compose during the initial screen-entry window play a brief upward translate (~8dp) + fade in, delayed by ~60ms per index. Items composed after the window (scrolled into view, swapped in by a background refresh, mutated in later) render statically — this is a one-shot welcome moment, never an "animate on scroll" effect. Wire it via the shared `rememberStaggeredEntryCoordinator` + `Modifier.staggeredEntry(coordinator, index)` (§4); compose it onto the item modifier alongside the mutation animator when both apply. Suppressed when system animations are disabled. **Hoist the `rememberStaggeredEntryCoordinator` call above whatever gates the loading/loaded swap** (an `if (isLoading)`, a `SkeletonCrossfade`) rather than inside the loaded branch — the coordinator stamps its first-composition timestamp the moment it is first remembered, so hoisting it to the section's outer scope stamps that timestamp at the section's own first paint (typically while still loading) instead of at content-arrival time. A network fetch usually clears the stagger's window before it resolves, so the item entrance defers to the crossfade below instead of compounding with it (an item fading and translating in while its parent section is *also* fading in reads as two overlapping animations, not one); the stagger still plays cleanly on the rare path where content is already on hand at first paint (no crossfade in play) — that is the "welcome" case it exists for. Explore's discovery rails (`ExploreScreenLayout.mobile.kt`) follow this shape.
- **Skeleton↔content crossfade, with the section's footprint reserved.** A section driven by a `loading*` boolean must never hard-swap `if (isLoading) skeleton else content` — wrap the swap in the shared `SkeletonCrossfade(isLoading, content: @Composable (Boolean) -> Unit)` (foundation `designsystem-core` `util/`) so the handoff is a ~150ms fade instead of a pop; suppressed under reduced motion like every other animation. Independently, the section's *presence* must be reserved for the entire loading phase — header plus a same-sized skeleton rail — so the section never appears from zero height once its data lands and shoves the rest of the feed down; only collapse to zero height once the section's own loading flag is false **and** it genuinely has nothing to show (the terminal empty case). Concretely: gate the early return on `isLoading.not() && <nothing to show>`, driven by the section's actual loading flag — never invert this into "any unresolved value implies still loading," which can never reach the terminal empty state once that value legitimately resolves to "nothing" (a stuck skeleton forever). Explore's "Because you read {genre}" rail is the motivating case: it used to gate on `if (genre == null) return` *before* even checking whether the rail was loading, so the whole section (header, skeleton, everything) rendered nothing until the genre resolved — then popped in at full height. The fix keeps the section's own `isLoading` flag as the single source of truth for the crossfade (so the header and rail reserve their footprint for the whole loading window regardless of whether `genre` happens to have arrived yet) and only tightens the terminal-empty check to `isLoading.not() && (genre == null || books.isEmpty())`, showing a header-shaped skeleton (`EditorialSectionHeaderSkeleton`, mirroring `EditorialSectionHeader`'s accent-bar/eyebrow/headline anatomy) while loading and collapsing only once loading is done and there is truly nothing to show. Finally, **a skeleton's dimensions must match its loaded counterpart's** — same rail height, same 2-line title reserved as two bars rather than one (a card's title `Text` using `minLines = 2` needs two skeleton bars, not one, or the crossfade shrinks when the real title lands), same trailing controls (a card with a button below its text needs a same-height button-shaped bar in its skeleton, not just the cover+title pair) — see `FeaturedCardSkeleton`/`RailCardSkeleton`/`SeriesCardSkeleton` in `feature/explore/.../ExploreShelf.kt` for worked examples of mirroring every row the loaded content renders, not just its leading art.
- **Cover-to-detail morph.** A tapped book cover on any source surface (library, explore carousels, reading) morphs into the book-detail hero cover via `Modifier.sharedBounds`. The morph is opt-in: pass `sharedTransitionKey = bookCoverTransitionKey(editionId, bookId)` to `EditionImage` at both source and destination. Both call sites must derive the same key — prefer edition id, fall back to book id. The destination paints the cover immediately from a `BookInitialCover` carried through navigation, so the morph never lands on an empty hero. The shared scopes (`LocalSharedTransitionScope`, `LocalNavAnimatedVisibilityScope`) are provided by the navigator shim in `RootScreen`; non-morphed pushes look identical to before. Do not apply the key to decorative `EditionImage` usages (e.g. blurred backdrops, full-screen cover viewer) — only to the tappable source cover and its detail hero.

### 2.6 Iconography

- Material outline icons, stroke weight consistent across the app. Never mix filled and outlined icon families on the same surface.
- Icon-only controls always carry a content description.
- Icon size scales with the control's size token (XS → XL); icons embedded in body type sit on the type baseline at a size proportional to the surrounding text.

**Icon tokens.** Icons are addressed through two design-system types, never through the platform resource system:

- `SoftcoverIcon` (`core/designsystem/presentation/icon/`) — the typed catalog of the bundled vector drawables (`SoftcoverIcon.Search`, `.Close`, …), backed by Compose Multiplatform resources (the underlying `Res` is internal to the module, so it resolves identically on Android and iOS).
- `RhaydusIconResource` (foundation `designsystem-core`, `nl.rhaydus.designsystem.icon`) — the icon *token* passed to components and drawn at call sites. It is a sealed type carrying a `contentDescription` plus one of: `Drawable(resource: DrawableResource)` (a catalog vector), `Vector(vector: ImageVector)`, or `Custom(painter: Painter)`. Build the catalog-vector case from a `SoftcoverIcon` via the app bridge `drawableIconResource(contentDescription, icon)` (`core/designsystem/presentation/icon/`), which resolves the catalog's internal `DrawableResource` so call sites still pass the typed `SoftcoverIcon` and the CMP resource stays module-internal. Always draw through the token — `Icon(painter = token.getIconPainter(), contentDescription = token.contentDescription, …)` — so the content description always travels with the icon and the catalog-vector / arbitrary-painter distinction stays meaningful. Do **not** reach for a raw `painterResource`/`SoftcoverIcon`-to-`Painter` shortcut at a draw site, and components that accept an icon take a `RhaydusIconResource`, not a bare `SoftcoverIcon`.
- A handful of icons that feed **Android-only** sinks a Compose painter can't reach — the foreground-service notification (`ic_reading`/`ic_play`/`ic_pause`/`ic_stop`/`ic_edit`) and the app's notification appearance (`ic_bookmark`) — are intentionally kept as Android `R.drawable` resources in `core:designsystem`'s `androidMain` as well; everything Compose goes through `SoftcoverIcon`.

**Illustrations.** Full-bleed editorial artwork, when a surface calls for it, is addressed the same way — through a design-system catalog, never the platform resource system. Onboarding ("Onboarding 1b") retired its intro-panel illustrations in favour of type-led hero copy, so the catalog below currently has no active consumer; it remains available for a future full-bleed surface (e.g. an empty state) rather than being deleted outright:

- `SoftcoverIllustration` (`core/designsystem/presentation/illustration/`) — the typed catalog of bundled illustration drawables (`SoftcoverIllustration.Writing`, `.SignUp`, …), backed by Compose Multiplatform resources with the underlying `Res` kept internal to the module, so the artwork resolves identically on Android and iOS. Draw through its `@Composable painter()` accessor — `Image(painter = illustration.painter(), contentDescription = …)` — and pass the contextual content description at the call site; never reach for a raw `painterResource` at the draw site.

### 2.7 Window size & breakpoints

The app runs on phones, tablets, foldables, and resizable desktop windows, so every surface adapts to the width it is given. Width is bucketed into three classes, and these are the **only** sanctioned breakpoints — a screen reads the class, it never hardcodes a dp threshold:

- **Compact — `< 600dp`.** Phones in portrait, narrow windows. The canonical bottom-bar shell.
- **Medium — `600–840dp`.** Large phones in landscape, small tablets, medium desktop windows. The navigation rail replaces the bottom bar.
- **Expanded — `>= 840dp`.** Tablets, unfolded foldables, desktop windows. A permanent editorial sidebar replaces the rail, and root list surfaces gain a side-by-side detail (the **list–detail two-pane** pattern, §5).

The class is read through `rememberWindowSizeClass()` (foundation `designsystem-core`, `nl.rhaydus.designsystem.layout`), which recomputes as the window resizes or a device folds. It exposes the bucketed `widthClass` plus the measured `widthDp` / `heightDp` for the rare *continuous* sizing decision (a hero whose height tracks the viewport) — reach for the class first; fall back to the measured value only when a discrete bucket genuinely can't express the layout. The navigation chrome progression is fixed: **bottom bar (compact) → rail (medium) → sidebar (expanded)**; the docked/floating bottom-bar preference (§4) only applies in compact.
