# Patterns — Library editing modes

Bulk-select and rearrange are the two editing modes a Library shelf can enter; see `patterns/library.md` for the masthead, sheets, and grid these modes sit inside.

### Bulk-select mode

Long-press a cover on a built-in shelf tab (All / Want-to-Read / Currently Reading / Read) to enter selection mode — **on desktop, where long-press is invisible to a pointer, entry is via right-click → "Select" or Ctrl/Cmd-click, with Shift-click range select (§2.5 desktop selection); the desktop right-click menu also exposes the per-book operations directly.** The masthead control line's Select circle (`patterns/library.md`) is a third entry point — it opens with an empty selection rather than seeding a book, since it has no pressed cover to anchor to. Fire `Haptics.threshold()` at activation, `Haptics.select()` on every subsequent toggle, `Haptics.commit()` when the user applies a bulk action. The page header swaps to a **selection header**: a 38dp `surfaceContainerHigh` × circle to exit, an italic `headlineSmall` "N selected" count, then a row of labelled 44dp `surfaceContainerHigh` action pills — **Move** (icon + label, opens a dropdown of move-shelf targets) and **Add to list** (icon + label, opens the shared `ChooseListsBottomSheet`) sharing the row's width, plus a 44dp `surfaceContainerHigh` trash circle (`primary` glyph, opens a confirmation `AlertDialog`). The masthead title/chevron, persistent search, control line, and filter chip row all hide while in selection mode. Back press, the exit circle, switching tabs, and deselecting the last book all exit. Per-cover anatomy: unselected covers dim to ~0.55 alpha; a selected cover gets an inset 3dp `primary` ring + a 16% `primary` wash over the (undimmed) cover, plus a 26dp circular badge at the top-end (filled `primary` with `ic_check` for selected, translucent `surface` ring for unselected). For `LIST_COMPACT` rows (kept only for back-compat — see "Library layout model" in `patterns/library.md`; the Arrange sheet does not offer it as a choice) the badge stays a leading position before the title with no ring/wash. The add-to-list sheet uses the same surface as book detail, generalised to accept a `Set<bookId>` and to render tristate membership per list (none / partial / all — tapping commits toward the larger end, matching the standard tristate-checkbox UX); after a successful toggle the surface stays in selection mode so consecutive adds across multiple lists feel like one operation. Custom-list tabs (which render editions rather than books) do not opt into selection — long-press is a no-op there, and the control line's Select circle is omitted on those tabs. Reach for this pattern whenever a root list surface needs N-target operations; do not invent a per-screen variant.

### Rearrange mode

A transient editing mode that gates drag-to-reorder behind an explicit opt-in, so a positional sort (MANUAL on a built-in shelf, ORDER on a ranked custom list) renders *display-only* by default — normal scroll/tap/long-press, no drag handles — and the order can't be nudged while browsing. Entered and exited from the **inline "Reorder"/"Done" hint chip** in the masthead control line (`patterns/library.md`): it appears only when the current tab is on a positional sort with ≥2 visible items, reads as plain chrome when idle and fills to `secondaryContainer`/`onSecondaryContainer` while rearranging — the one chip is both the entry and the `Done` exit. Entering reveals the per-card drag handles (see the two "Drag-to-reorder" patterns below for handle anatomy and persistence); the mode is **drag-only** — tap-to-open and long-press-to-select are suppressed so the gesture vocabulary stays unambiguous while handles are live. Crucially, entering/leaving the mode must **not** swap the grid for a different composable: the display and reorder states are rendered by the **same** grid node (items only gain a handle and drop their tap targets), because disposing one grid and composing another remounts every cover's image and flashes the screen. Exits on the button (now `Done`), system back, switching tabs, or changing the sort. It is **mutually exclusive with bulk-select** (entering either clears the other) — reach for it whenever a surface offers an in-place reorder that would otherwise let casual scrolling perturb the order; do not leave always-live drag handles on a freely-scrolling grid.

### Drag-to-reorder shelf (built-in shelves, MANUAL)

Used on the built-in Library shelves (Want-to-Read, Currently Reading, Read) when the tab's sort mode is `MANUAL`. MANUAL is offered in the Arrange sheet's sort chips only for those three shelves — the All tab and Did Not Finish suppress it; custom-list tabs use the separate `ORDER` mode below — and its chip carries no direction chevron because the stored position itself is the order. **Selecting MANUAL is display-only:** the saved order renders with normal scroll, tap-to-open, and long-press-to-select intact and *no drag handles*, so the order can't be nudged while browsing. Dragging is gated behind an explicit **Rearrange mode** (above), entered from the masthead control line's "Reorder" hint chip. Only while rearranging does each card gain a grab affordance overlaid at its top-end: a circular `surfaceContainerHigh`-tinted pill (~28dp, 4dp padding, alpha 0.9, `onSurfaceVariant` content) wrapping an `ic_drag_handle` glyph, wired via `Modifier.draggableHandle(...)` from the `sh.calvin.reorderable` library. Pressing the handle fires `Haptics.lift()`, the reorder library snaps neighbouring cards into intermediate slots during the drag, and release fires `Haptics.drop()`. Rearrange mode is drag-only — tapping a cover does not navigate and long-press does not enter bulk-select, so the gesture vocabulary stays unambiguous while the handle is live (the long-press → bulk-select shortcut lives on the display-only path instead). Rearrange and bulk-select are mutually exclusive: entering one clears the other. Persistence is local-only and **prefix-scoped**: on drop, only positions `0..maxTouchedIndex` are written, where `maxTouchedIndex` is the deepest visual index any move spanned. Books beyond that depth retain whatever state they had (positioned or unsorted), so a shallow drag at the top of the shelf doesn't pin books the user never touched, and newcomers fetched from the API surface at the top of the unsorted region — immediately below the pinned prefix — rather than at the very bottom. Reach for this pattern wherever a grid surface needs an in-place reorder that coexists with a separate sort dimension and with bulk-select.

### Drag-to-reorder custom list (ORDER, ranked-gated)

The custom-list counterpart to the MANUAL shelf variant above, with two consequential differences. **(1) Server-owned positions:** the order lives on Hardcover's `list_books.position` column, not in a local-only table. **(2) Gated on the list's `ranked` flag:** the Arrange sheet's sort chips expose `ORDER` only when `lists.ranked = true`. Unranked custom lists show the four in-memory sorts (Title / Author / Page count / Release date) as chips, followed by a "✶ Make this list ordered" text affordance (`bodyMedium` tinted `primary`) that flips `ranked` to true via the `UpdateList` mutation. The flip is optimistic: the local cache toggles immediately, the tab's stored sort auto-switches to `ORDER` so the user lands directly on the reorderable grid, and the server call follows; on failure both are rolled back and a snackbar surfaces ("Couldn't enable manual ordering for "…" — try again."). Like MANUAL, `ORDER` is display-only until the user enters **Rearrange mode** from the masthead control line's "Reorder" hint chip (or the Arrange sheet's "✶ Make this list ordered" affordance, which flips `ranked` and auto-switches the sort to `ORDER` in one tap); drag anatomy and haptics then match the MANUAL variant (overlay handle, `lift` on grab, `drop` on release, drag-only with tap-to-open suppressed while the handle is live). Persistence is **range-scoped**, not prefix-scoped: on drop, only positions `[minTouchedIndex, maxTouchedIndex]` are rewritten (clear-then-set in a single GraphQL mutation that mirrors Hardcover web's two-step `update_list_books` + `update_list_books_many` pattern). Books outside the range keep their existing positions, so a swap of two adjacent middle items only touches those two slots on the server, never the rest of the list — matching the web client's semantics so two devices editing the same list don't fight each other. On server failure the optimistic local write stands and the next list refresh reconciles. Reach for this pattern wherever a server-owned ordered collection needs in-place reorder.
