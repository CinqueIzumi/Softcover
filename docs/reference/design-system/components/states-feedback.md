# Components — States & feedback

### Inline error state

`InlineErrorState(message, onRetry, modifier)` is the standard inline surface for a load or submit failure. It renders the `message` in the `error` color role (editorial `bodySmall` face, centered) and a full-width outlined **Retry** `RhaydusButton` (size S) below it, vertically centered within the space the caller supplies via `modifier`. It is consumed by any screen whose TOAD `UiState` carries a `String?` error-slot — drop it where the normal content would appear, not as an overlay. The caller passes a `() -> Unit` retry lambda that re-dispatches the appropriate `UiAction`; the component is oblivious to the action type. Reach for it on any inline load/submit-failure surface: explore search errors, onboarding key validation, and future `String?`-slotted screens. Do not hand-roll a per-screen error layout. It is the foundation `designsystem-core` component (`nl.rhaydus.designsystem.component.InlineErrorState`); the editorial `bodySmall` face is supplied by Softcover via the `textStyle` param (the foundation default is plain Material `bodySmall`), and the `retryLabel` default `"Retry"` is kept.

### Pull-to-refresh indicator

The Material 3 Expressive `ContainedLoadingIndicator` inside a `PullToRefreshDefaults.IndicatorBox` is the canonical pull-to-refresh affordance. This is a deliberate exception to the "wavy progress, always" rule (DS §2.5, §6): the wavy circular indicator visually competes with the pull gesture's own arc and reads as off at this size, while the contained loading indicator's morphing shape carries the same expressive character without the conflict. Reach for the wavy primitive everywhere else progress is shown.

### Pull-to-refresh eyebrow

`PullToRefreshEyebrow` is the canonical eyebrow for any screen that hosts a pull-to-refresh surface. It lives in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`). It renders the same accent-bar + eyebrow anatomy as a static `SectionHeader`, but swaps the label to a contextual refresh copy ("Refreshing your shelf…", "Catching up on your reading…") while the user pulls and during the subsequent refresh, then flashes the base label briefly in italic on revert. Wired internally: the eyebrow consumes the same `PullToRefreshState` already passed to `PullToRefreshBox`, listens to its `distanceFraction`, and fires a single `threshold` haptic at the trigger crossing (re-armed once the gesture relaxes). Reach for it on every refreshable root surface; do not hand-roll the eyebrow swap or the trigger haptic at call sites.

### Search results pagination

Explore's search-results list/grid (feature-owned) has no server-side total (the search endpoint returns no hit count), so paging is a "maybe more" append: a `LaunchedEffect` + `snapshotFlow` over the list/grid state's `layoutInfo.visibleItemsInfo.lastOrNull()?.index` dispatches the "load next page" action once the visible window comes within a fixed item-count threshold of the fetched end, gated on a `hasMore` flag from state. A tail `CircularWavyProgressIndicator` (full-width row on mobile's `LazyColumn`, a `GridItemSpan(maxLineSpan)` row on desktop's `LazyVerticalGrid`) shows while the append fetch is in flight and disappears once `hasMore` goes false. There is deliberately **no "N of M" count** anywhere in this surface — only the append spinner and its disappearance communicate paging state.

### Connectivity chrome

The offline report is two components plus one state read, deliberately split across two modules. `Banner` + `offlineBannerUiModel(visible)` (the transient "you're offline" strip the app shell raises in `RootScreen`) and `EmptyState` + `offlineEmptyStateUiModel()` (the placeholder for a screen whose content cannot load offline) are **`core:component` components** (`callout/`, `state/` — see their KDoc for the contract). `rememberIsOnline()` lives in **`core:presentation`** (`connectivity/`), because reading network availability means resolving a provider out of DI and the component library may not reach for DI (§7.4); it is consumed by the shell and by any feature screen that must degrade offline (`explore`, `book_detail`). Reach for `EmptyState` with the offline model for any "needs the network" empty state; do not hand-roll a per-screen offline placeholder.

### Update highlight card

The Settings screen's `primaryContainer` editorial highlight (`AppUpdateSection`), shown only while an app update is not `Idle`. This is a **second, distinct tinted-card convention from the primary-filled hero stat card** (§2.1): where the hero stat fills solid `primary` and is capped at one per scrollable region, this card fills `primaryContainer` / `onPrimaryContainer` (radius 12dp) and is reserved for this one system-status callout. Anatomy: a hand-composed accent-bar + all-caps Inter eyebrow (not `SectionHeader`'s Section register, since its headline is fixed to `onSurface` and this card needs `onPrimaryContainer`), an italic Fraunces headline, and a state body — a fully-rounded `Surface(onClick, shape = percent(50))` pill action (`primary` / `onPrimary`, the same anatomy as `Chip` and the Library control-line pills) for Available/Downloaded/Failed, or an **indeterminate** `LinearWavyProgressIndicator` (`primary` stroke / `outlineVariant` track, no percentage) while Downloading — the client has no reliable version string or download percentage to show, so headlines and copy are deliberately version-less ("A new version is ready", never "Version 3.2.0"). No badge, no chevron, no whole-card click — the pill (or the absence of one, while downloading) is the only affordance.
