# Components — Rich text

## Parked for KDoc (Step 07d)

### Clickable text

`ClickableText(model: ClickableTextUiModel, onEvent, style, inlineContent)` (`core:component`, `richtext/`; the `style` parameter is an R11 holdout scheduled for the contract retrofit — it belongs on the model) is the canonical way to render prose with a tappable substring: it resolves `url` string annotations in the model's `AnnotatedString` to taps and reports the annotation's payload as `ClickableTextEvent.LinkClicked(url)`, so a screen never wires its own `pointerInput`/`detectTapGestures` for an inline link. Its `inlineContent: Map<String, InlineTextContent>` param (empty by default) is forwarded to the underlying `Text` unchanged, so a call site can glue a small glyph directly onto a run of text via `AnnotatedString.appendInlineContent(...)` — e.g. onboarding's "Find your key … here[external-link glyph]." helper line glues an external-link icon straight after the "here" link with no gap. Reach for this whenever a glyph needs to sit *inside* a sentence rather than as a separate leading/trailing icon.

### Rich text

`RichText(model: RichTextUiModel, …)` (`core:component`, `richtext/`; its trailing `style` / `color` / `maxLines` / `overflow` / `onClick` / `onTextLayout` parameters are R11 holdouts scheduled for the contract retrofit — they belong on the model) is the canonical renderer for formatted prose wherever it is displayed read-only — a stored review on `VerdictBlock` and on community review cards, and the reader's review on the reading-update share card. It is named for what it renders, not for where the text came from: nothing about formatted prose is specific to a review. Its model is the library's own (`RichTextUiModel` — paragraphs of runs carrying bold / italic / spoiler marks); a feature holding a `ReviewDocument` maps through `:core:uibinding`'s `toRichTextUiModel()` first, and back through `toReviewDocument()` when the reader has edited it. That pair is the only bridge, and the reason it exists is R4: a component may not name a domain type. The base face is **upright** (italic is a per-run mark, not the default voice); bold and italic runs are styled inline; a run marked as a spoiler is hidden under a solid `spoilerCover` block (text drawn transparent over the block) until the reader **taps that span** to reveal it, tracked as transient per-span state. This inline reveal is independent of any whole-review "Show spoiler" gate the caller wraps around it. A tap that does *not* land on a concealed spoiler invokes the optional `onClick` (so the surrounding card still opens on tap). It exposes `maxLines` / `overflow` / `onTextLayout` so callers can drive their own "Show more" affordance. Reach for it for any displayed review body; never render review content through `htmlToAnnotatedString` (that path is for server HTML like book descriptions, not reviews).

### Rich-text formatting toolbar

`RichTextFormattingToolbar` (`core:component`, `control/` — it is only ever used inside `VerdictSheet`) is the inline bold / italic / spoiler control row for the review editor. It uses the app's pill-chip anatomy (§3.4 / inline filter chip strip): three fully-rounded **word toggles** — `Bold` (rendered bold), `Italic` (rendered italic), `Spoiler` — so the row reads as one deliberate control rather than loose buttons, and the bold/italic chips preview their own effect. Active → `secondaryContainer` / `onSecondaryContainer` (the app's standard selected-chip colours); idle → `surfaceContainer` / `onSurfaceVariant`. Each chip reflects whether the *whole current selection* already carries that mark; with no selection to act on the entire row dims (≈0.45 alpha) and is inert. Reach for it only inside `VerdictSheet`; it is not a generic rich-text bar.
