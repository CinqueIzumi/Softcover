# Design System — Components

## 4. Components

A short catalogue of shared components and what role they play. Anatomy and styling live with the components; this list is so a designer or contributor knows *which* tool to reach for.

- **Top app bar** — page title, optional subtitle, optional back, optional trailing icon actions. Title autosizes within `titleLarge`.
- **Search top app bar** — `SoftcoverSearchTopBar`, the mobile search chrome; see §3.1 for the authoritative anatomy. It is a full-width `Surface` holding a `Row` of a bespoke search pill (leading search glyph, `BasicTextField`, and a trailing slot carrying either the clear (✕) or the wavy circular loading indicator) beside a persistent barcode-scan button. The scan action sits at `Row` level *beside* the pill — not inside it — because the pill's single trailing slot is spoken for. Its focus contract is the part to get right: the caller's `focused` state drives the platform field (never the reverse), and `onSearchActivated` / `onSearchDismissed` / `onClearSearch` are intents rather than focus notifications — see §3.1.
- **Editorial search field** — `EditorialSearchField` is the canonical *inline* search input for surfaces that carry their own editorial header rather than a Material search top bar: a fully-rounded `surfaceContainer` pill holding a leading search glyph, a single-line `BasicTextField`, and a trailing clear (✕) button that appears only once there is a query. It lives in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`) and is consumed by the desktop Library and desktop Explore headers. The caller supplies the icons as `RhaydusIconResource` (`searchIcon`, `clearIcon`); the empty-state hint adapts via `placeholder` ("Search your collection" on Library, "Search books, authors…" on Explore). Library renders it **persistently** on both mobile and desktop — no toggle icon, no hidden search affordance — per the masthead pattern below (a large collection needs a findable front door). Reach for it when a static editorial layout wants a persistent search field beneath its title; use the **Search top app bar** instead when search *is* the app bar (the mobile pattern).
- **Desktop tooltip** — `DesktopTooltip(text) { control }` wraps an icon-only control in a hover tooltip on desktop and is a no-op pass-through on touch (§2.5 desktop tooltip). Reach for it on every icon-only desktop control; controls with a visible text label do not get one.
- **Desktop context menu** — `DesktopContextMenu(items) { surface }` wraps a surface in a right-click menu on desktop (`ContextMenuArea`) and is a no-op pass-through on touch (and when `items` is empty), §2.5 desktop selection. `DesktopContextMenuItem(label, onClick)` is one entry. Reach for it for the desktop secondary-click affordance on an item that touch reaches via long-press.
- **Bottom navigation** — tab destinations for the four roots, the **compact-width** chrome (§2.7). Provided as a docked bar (full-width, attached to the system inset) and a floating toolbar variant; pick docked unless the screen explicitly calls for a hovering bar over scrolling media. The two are **placements of one host**, not two shells: `CompactNavShell` renders a single foundation `BottomBarScaffold` and maps the user's `BottomBarStyle` preference onto `BottomBarPlacement.DOCKED` / `.OVERLAY`, so flipping the preference re-places the bar without relocating the tab body (which would tear down and rebuild the live tab). The rendered bar itself is **app-shell code, not a `core/presentation/component`** — `DockedBottomNavigationBar` / `BottomFloatingBar` live at the orchestration tier (`orchestration/presentation/`) alongside the `TabNavigator` host, because they enumerate the concrete feature tabs. Reusable building blocks they rely on (`RhaydusIconToggleButton`, icon/color roles) stay in `core`. The floating variant's tap shield (a transparent `clickable` around the pill, so taps in the gaps never fall through to the content scrolling beneath) is part of the bar chrome, not the host.
- **Navigation rail** — the **medium-width** chrome (§2.7): a vertical `NavigationRail` that replaces the bottom bar between 600 and 840dp. Same destinations, selection, app-update badge, and library pulse as the bottom bars.
- **Editorial sidebar** — the **expanded-width** chrome (§2.7): a permanent sidebar (`>= 840dp`) carrying the app wordmark in the editorial `pageTitle` voice over the four destinations, each a selectable row in the app's selected-chip colours (`secondaryContainer` / `onSecondaryContainer` when active, `onSurfaceVariant` idle). Replaces the rail. Like the bottom bars, the rail and sidebar are **app-shell code at the orchestration tier** — they enumerate the concrete feature tabs. All four chromes are driven by one shared `rememberNavItems()` source (`orchestration/presentation/`) so selection, badge, and pulse can never drift between them; the reusable building blocks stay in `core`.
- **Button** — five styles (filled, tonal, elevated, outlined, text) across five sizes (XS → XL). Filled is the page's primary action; tonal is a secondary action that still wants weight; outlined and text are tertiary. One filled action per region — never two competing primaries.
- **Toggle button / icon toggle button** — same size scale as Button; the active state expresses itself via shape morph and fill, not via a separate badge.
- **Split button** — a single primary action paired with an attached chevron that opens a menu of related variants (e.g. "Mark as reading" + alternative shelves). Reach for it when an action has one obvious default and a small set of equivalents.
- **Pill chip** — `PillChip` is the canonical fully-rounded (`RoundedCornerShape(percent = 50)`) chip: a `Surface` carrying a single `labelMedium` label. It backs both the library filter facets and the book-detail tag chips, so the chip anatomy lives in one place — reach for it instead of hand-rolling a `Surface`-and-`Text` pill. Selected → `secondaryContainer` / `onSecondaryContainer` (label semibold); idle → `surfaceContainerHigh` / `onSurface` (label medium). *(This is the authoritative idle colour for the pill-chip anatomy; older prose that says `surfaceContainer` / `onSurfaceVariant` for unselected chips predates the extraction and should be read as `surfaceContainerHigh` / `onSurface`.)* Pass `onClick` for an interactive chip (toggles, filters); omit it for a **read-only** chip — the surface then carries no ripple and no click role, the mode used for the book-detail tag chips. A `concealed` flag renders the chip as a **spoiler redaction** (§2.1 spoiler register): the label is drawn `Color.Transparent` so it still reserves its width but cannot be read, beneath a solid `spoilerCover` fill — the same treatment `ReviewDocumentText` gives an inline spoiler run. Because the hidden label still measures at full width, revealing it (re-render with `concealed = false`) does not reflow the row. Used for book-detail content-warning chips.
- **Expandable flow row** — `ExpandableFlowRow` is the canonical wrapping chip/tag container for a set that can grow unbounded. It wraps items across lines and, past `collapsedLines`, collapses to that many lines behind a trailing **"show more"** affordance; each tap reveals `linesPerExpand` more lines until everything shows and the affordance disappears — a *gradual*, line-based reveal (built on `FlowRow`'s `maxLines` + `FlowRowOverflow.expandIndicator`), so a long set never buries the content beneath it. Both bounds are caller-set; the trailing affordance defaults to an editorial `surfaceContainerHigh` / `primary` pill matching `PillChip`'s anatomy but can be replaced via `showMoreIndicator`. Its `content` is a plain slot (no `FlowRowScope` receiver) so a call site needs no experimental opt-in. The library filter's facet chips use it on the desktop panel form (§3.5) — where a fixed-width panel can't scroll a chip row sideways — while the narrow bottom sheet keeps each facet on one horizontally scrolling line. Reach for it for any wrapping chip set that can run long; do not hand-roll a `FlowRow` with manual slice-and-count state. It is the foundation `designsystem-core` layout primitive (`nl.rhaydus.designsystem.layout.ExpandableFlowRow`); the default "show more" pill is the foundation's (label set via `showMoreLabel`), and the library filter call site uses it with all defaults.
- **Edition image** — the canonical book cover. Always 2:3 aspect, subtle radius, optional soft shadow tinted by edition. Falls back through edition → default edition → URL → shimmer placeholder. A final **coverless-title** rung via `coverlessTitle`: when no source resolves (or a known URL fails to load) and the data is not still loading, the cover falls back to the shared **Coverless title cover** component (below) instead of a blank tile. **A cover slot is never blank** — `coverlessTitle: String?` is a **required parameter with no default**, precisely so this rule is enforced at the call site rather than remembered: every surface rendering a real, readable cover must pass it, or the code does not compile. The one documented exception is the blurred decorative backdrop behind the book-detail hero (`GeneralBookInfoSection`'s `matchParentSize().blur(...)` layer): it is never read as a cover itself, so a title rendered there would just be blurred noise, and it passes `coverlessTitle = null` explicitly, with a comment explaining why. An optional `maxDecodePx: Int` parameter (default `null`) caps the Coil decode size for the underlying image request; pass a value (e.g. `600`) from grid call sites to prevent bitmap over-allocation for small tiles, and omit it for large detail-screen covers where full resolution is wanted. Never use a raw image loader for covers.
- **Coverless title cover** — `CoverlessTitleCover(title, modifier)` is the standalone component behind `EditionImage`'s coverless-title rung; every non-decorative cover call site reaches it that way rather than instantiating it directly (the tag-editor jacket and the explore hidden-suggestions shelf thumbnails at 48–52dp included). It renders the **monogram jacket**: a fixed-ink `MonogramCoverInk` panel (§2.1), an inset hairline `MonogramCoverForeground`-at-0.24-alpha border, and — at or above the component's full-title width floor — the **whole title** set large in italic Fraunces (`editorialTypography.headlineMedium`), centred and wrapped across lines. **Keyed purely on "no cover art resolves," never on release status** — an unreleased book with a real jacket shows that jacket like any other book; the monogram is reached only when no source resolves or a known URL fails to load, and only after loading has finished. It is **size-adaptive, with a graceful degrade to a single initial**: a `BoxWithConstraints` measures the tile it is given and derives the border inset, the full title's starting font size / line cap, and the single-initial fallback's font size purely from that measurement (`monogramCoverMetrics`, pure and independently tested). The full title renders via `TextAutoSize`, which shrinks the font further — down to a shared 10sp legibility floor — to fit the tile's measured width, ellipsizing if it still overflows the line cap; below the width floor (a tile too small to fit even a couple of legible words, e.g. a ~48dp shelf thumbnail) it falls back to the title's first letter set large instead, the original single-initial treatment. One component therefore serves everything from a 48dp shelf thumbnail (initial only) up through the widest real library grid tile (full title) with no per-call-site tuning. It imposes **no aspect ratio of its own**; it fills whatever box its `modifier` and the surrounding layout give it — `EditionImage` applies the 2:3 cover aspect on its own container before falling back to it.
- **Inline error state** — `InlineErrorState(message, onRetry, modifier)` is the standard inline surface for a load or submit failure. It renders the `message` in the `error` color role (editorial `bodySmall` face, centered) and a full-width outlined **Retry** `RhaydusButton` (size S) below it, vertically centered within the space the caller supplies via `modifier`. It is consumed by any screen whose TOAD `UiState` carries a `String?` error-slot — drop it where the normal content would appear, not as an overlay. The caller passes a `() -> Unit` retry lambda that re-dispatches the appropriate `UiAction`; the component is oblivious to the action type. Reach for it on any inline load/submit-failure surface: explore search errors, onboarding key validation, and future `String?`-slotted screens. Do not hand-roll a per-screen error layout. It is the foundation `designsystem-core` component (`nl.rhaydus.designsystem.component.InlineErrorState`); the editorial `bodySmall` face is supplied by Softcover via the `textStyle` param (the foundation default is plain Material `bodySmall`), and the `retryLabel` default `"Retry"` is kept.
- **Clickable text** — `ClickableText(annotatedText, style, handleUrlClick, inlineContent)` (app-owned, `core/designsystem`'s `presentation/component`) is the canonical way to render prose with a tappable substring: it resolves `url` string annotations in `annotatedText` to taps and forwards the annotation's payload to `handleUrlClick`, so a screen never wires its own `pointerInput`/`detectTapGestures` for an inline link. Its `inlineContent: Map<String, InlineTextContent>` param (empty by default) is forwarded to the underlying `Text` unchanged, so a call site can glue a small glyph directly onto a run of text via `AnnotatedString.appendInlineContent(...)` — e.g. onboarding's "Find your key … here[external-link glyph]." helper line glues an external-link icon straight after the "here" link with no gap. Reach for this whenever a glyph needs to sit *inside* a sentence rather than as a separate leading/trailing icon; the Library tabs group subhead's inline `primary` dot (above) predates this param and still hand-rolls its own `Text(inlineContent = …)` wiring — a future touch to that surface should move it onto `ClickableText` rather than a second surface reinventing the same wiring.
- **Loading dialog** — full-screen blocking wavy progress indicator for unavoidable waits; prefer inline shimmer on cards when the wait is short or the surface can stay interactive.
- **Pull-to-refresh indicator** — the Material 3 Expressive `ContainedLoadingIndicator` inside a `PullToRefreshDefaults.IndicatorBox` is the canonical pull-to-refresh affordance. This is a deliberate exception to the "wavy progress, always" rule (DS §2.5, §6): the wavy circular indicator visually competes with the pull gesture's own arc and reads as off at this size, while the contained loading indicator's morphing shape carries the same expressive character without the conflict. Reach for the wavy primitive everywhere else progress is shown.
- **Pull-to-refresh eyebrow** — `PullToRefreshEyebrow` is the canonical eyebrow for any screen that hosts a pull-to-refresh surface. It lives in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`). It renders the same accent-bar + eyebrow anatomy as a static `SectionLabel`, but swaps the label to a contextual refresh copy ("Refreshing your shelf…", "Catching up on your reading…") while the user pulls and during the subsequent refresh, then flashes the base label briefly in italic on revert. Wired internally: the eyebrow consumes the same `PullToRefreshState` already passed to `PullToRefreshBox`, listens to its `distanceFraction`, and fires a single `threshold` haptic at the trigger crossing (re-armed once the gesture relaxes). Reach for it on every refreshable root surface; do not hand-roll the eyebrow swap or the trigger haptic at call sites.
- **Rhaydus shimmer image** — the canonical loader for non-cover images (avatars, author photos, any free-aspect imagery). Provided by the foundation **`designsystem-image`** module (`nl.rhaydus.designsystem.image.RhaydusShimmerImage`). Use it rather than reaching for a raw image library; it shares the project's Coil loader, shimmer placeholder (suppressed under reduced motion), and `SkeletonCrossfade` behavior. Signature: `(model: Any?, contentDescription: String?, modifier, contentScale, isLoading)`. `EditionImage` is for book covers only — everything else uses `RhaydusShimmerImage`.
- **Update progress sheet** — modal sheet for editing reading progress. Hosts the canonical `pages | percentage | time` segmented switcher with a hero numeric input, an editorial suffix line, and a wavy progress bar. The switcher is **format- and total-aware**: the primary unit is `time` for an audiobook (`BookEdition.isAudiobook`, which is keyed off the edition's `ReadingFormat`, not whether a duration happens to be present) and `pages` otherwise, and `percentage` is offered **only when the matching total is known** (page count for print, duration for audio) — without it a fraction can only ever resolve to 0, so the tab is hidden rather than shown broken. When that total is unknown the sheet drops to the primary unit alone, hides the "of N …" suffix and the progress bar, and accepts free numeric/time entry (no clamp-to-total). New "edit a single number on a book" surfaces should look at this sheet before inventing a new one. **Stepper circles.** The Page and Percentage tabs flank the hero number with a pair of 44dp circular `surfaceContainerHigh` `−` / `+` steppers (primary glyph), stepping the value by 1 (page or percent) and reusing the same clamp bounds (`[0, total]` / `[0, 100]`) the typed-entry path already enforces. The Time tab carries the same stepper pair around its minutes field only, stepping by 1 minute — hours and seconds stay typed-entry only. A stepper tap writes straight into the tab's existing `TextFieldValue` state, so it composes with typed entry rather than branching around it. **Mark as read.** A standard secondary action, present on **every** progress sheet — an outlined `RhaydusButton` (`ButtonStyle.OUTLINED`, a check icon, label "Mark as read") sits below the tab content's own "Update progress" filled action. `onMarkAsReadClick: () -> Unit` is a **required** parameter (not optional) — every call site must wire it; there is no way to render the sheet without it. Both current consumers route it to their existing per-book mark-as-read path rather than introducing a new one: Reading wires it to the same commit choreography a book's row/hero "mark as read" affordance always used (haptic, burst, bottom-bar pulse, and the "slide to shelf" follow-through when motion is enabled, §2.5) rather than a bare action dispatch, so marking as read from the sheet feels identical to marking it as read from a shelf control; Book Detail dispatches the same action its Shelve control's "Read" row fires, whose commit haptic + `MarkAsReadBurst` celebration is already driven screen-wide off the ScreenModel's mark-as-read event (not by anything local to that row), so the sheet gets the identical celebration for free.
- **Editable hero-stat field** — `HeroStatNumberField` is the shared "edit a single number framed as a hero" control (with its `EditorialSuffix` caption): a borderless `BasicTextField` rendered in the editorial `statLarge` face, cursor tinted `primary`, width sized to the character count so it reads as a hero numeral rather than a boxed form field. Both live in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`). It is the canonical input behind both the Update progress sheet and Focus Mode's page entry. Reach for it for any number the user edits in a hero context; **never** use a bordered `OutlinedTextField`/`TextField` for that role — the box clashes with the editorial register.
- **Deadline badge / cover overlay / summary line** — the family of components that mark a book as time-bound. Used together when a book's deadline matters; never mixed with a stale rating row in the same card. **Library's grid/cover-only cells use a distinct countdown badge instead** (a Library-local composable, not this shared family): top-**start**, `primary`/`onPrimary` fill (`errorContainer`/`onErrorContainer` while behind schedule — a deliberate deviation from the redesign spec's single-primary badge, kept because the app already reserves error for "needs attention" everywhere else), a calendar glyph (`SoftcoverIcon.DateRange`) + "N days" (a duration, not a date — "Aug 28" reads like a release date, "9 days" reads as time remaining), reading "Expired" once the deadline has passed. The two badges are not swapped project-wide: Reading and Book detail keep the original top-end status-label `DeadlineBadge` (`OnTrack`/`Behind`/`Expired`) unchanged; only Library's grid cells use the countdown. Library's List (large) row shows neither badge — its wavy shelf-progress line (below) already carries the book's reading state, and a redundant deadline-date line would be the row's third stat.
- **Unreleased badge** — `UnreleasedBadge` is the canonical mark for a book whose effective release date is in the future. Two styles: `Compact` ("Out MMM d", with year appended only when not the current year) sits as a top-start overlay on cover art in carousels and grid cards — including Explore's Up-next lead card once it isn't yet released, which names its date the same way every other unreleased rail card does rather than a generic "Coming soon"; `Prominent` ("Releases MMMM d, yyyy") sits inline beneath the hero byline on book detail. Surface is `primary` / `onPrimary` so the chip reads as a deliberate publishing signal rather than another deadline state. When the prominent variant is shown on book detail, suppress the trailing release year in the byline so the date isn't named twice. The "is it unreleased?" check is centralised on `Book.isUnreleased` — never compare dates at the call site.
- **Browse-by-mood grid** — Explore's 2-column mood-tile grid (`MoodGrid`/`MoodTile`): tiles are `16dp`-padded, `104dp`-min-height, `16dp`-radius, and each row is measured at `IntrinsicSize.Max` with both cells `fillMaxHeight()` so two titles wrapping to a different line count still land at the same row height. Anatomy top-to-bottom: a `MOOD` eyebrow + a small search glyph on one row, then the title (the mood-tile title exception, §2.2) and a book-count subline (`formatGroupedNumber`, grouped thousands — never a hand-rolled digit string). Ink cycles through the four fixed looks in §2.1 by tile position (index mod 4), repeating past the fourth tile rather than introducing a new colour. Mood labels arrive from the API lowercase; the render layer title-cases each whitespace-separated word before it reaches a `Text` — the domain model itself is never mutated. A tap always runs a mood-filtered search (never its own feed rail).
- **Search results pagination** — Explore's search-results list/grid has no server-side total (the search endpoint returns no hit count), so paging is a "maybe more" append: a `LaunchedEffect` + `snapshotFlow` over the list/grid state's `layoutInfo.visibleItemsInfo.lastOrNull()?.index` dispatches the "load next page" action once the visible window comes within a fixed item-count threshold of the fetched end, gated on a `hasMore` flag from state. A tail `CircularWavyProgressIndicator` (full-width row on mobile's `LazyColumn`, a `GridItemSpan(maxLineSpan)` row on desktop's `LazyVerticalGrid`) shows while the append fetch is in flight and disappears once `hasMore` goes false. There is deliberately **no "N of M" count** anywhere in this surface — only the append spinner and its disappearance communicate paging state.
- **Because-you-read genre picker** — Explore's "because you read {genre}" section lets the reader override the auto-derived genre via a **bottom sheet mirroring Library's own Shelves sheet pattern** (§5), rather than a bespoke dropdown or pill row. The anchor is the same compact `eyebrowSmall` label naming the resolved genre with a trailing `primary` chevron (`"Genre · {genre}"`, uppercase) the earlier dropdown used, but tapping it now opens an `AdaptiveModalSheet` instead of a `DropdownMenu`. The sheet's own header is a canonical editorial header (accent bar + "GENRE" eyebrow + "Pick a genre" headline — a short neutral category word rather than repeating the rail's "Because you read" name, which read as redundant and option-like once opened inside the sheet) over a vertical list of hairline-divided rows — exactly the Shelves sheet's row anatomy (`titleLarge` forced-italic label, promoted `primary` + trailing check glyph on the active row) minus the leading shelf-type glyph and trailing item count, neither of which a genre has. The first row is always "Auto (most-read)" (clearing the override back to the derived default, checked whenever the resolved genre isn't one of the switchable options); one row per switchable genre option follows. Tapping a row dispatches the selection and dismisses the sheet through `LocalModalSheetDismiss`; the sheet's open/closed flag is plain `remember`ed UI-local state. Hidden entirely when there are no genre options to switch between.
- **Bookmark toggle** — a 44×44dp, 12dp-radius add/remove-from-library control: unset is `surfaceContainerHigh` fill with a `primary` glyph (`SoftcoverIcon.BookmarkAdd`), set is `primary` fill with an `onPrimary` glyph (`SoftcoverIcon.BookmarkAdded`). Used on Explore's search-result rows; reach for it on any other row-style book listing that offers an inline add/remove-from-library action rather than hand-rolling an `IconToggleButton`.
- **Haptics helper** — the single entry point for haptic feedback. Exposes eight semantic cases. No ad-hoc haptics — never call `performHapticFeedback` from a call site; always go through the helper. The "no mixed icon families" rule (§2.6) has a sibling here.
  - **commit** — a user-triggered action succeeded (mark-as-read, save, confirm). Celebratory in texture; reserved for commit-class actions, never navigation taps.
  - **reject** — an optimistic mutation rolled back, or an action refused. Pair with the shake-on-error visual (§2.5).
  - **select** — a soft tick on neutral selection: shelf chip toggle to a non-read state, segmented switch in a sheet, tab change in a carousel filter. Distinct from *commit* (which celebrates) and *reject* (which rolls back).
  - **threshold** — a single firm tap when the user crosses a meaningful boundary: pull-to-refresh trigger point, drag-to-reorder pickup, long-press peek activation. No celebratory texture.
  - **tickle** — a per-integer tick during a slider or picker drag. Each integer crossing on the rating control or progress page-number input fires one tick.
  - **lift** — drag-to-reorder pickup. Says the item has left the page; pair with the visual lift.
  - **drop** — drag-to-reorder settle. Distinguishable from *lift* so the item's return to the page is felt.
  - **milestone** — a two-pulse haptic above *commit* for natural progress events: completing a year-end reading goal, hitting a 30-day streak, finishing the last book in a series. Reserved for moments that are bigger than a save.
- **Mark-as-read celebration** — `MarkAsReadBurst` is the canonical hero moment for a successful mark-as-read commit. It paints a radial particle burst (primary + tertiary tinted) outward from the centre of its footprint; replays whenever `triggerKey` changes; suppressed under reduced-motion (§2.5). Compose it as a sibling overlay (`Modifier.matchParentSize()` or `Modifier.fillMaxSize()`) on whichever surface owns the commit — the shelf-action card on book detail and the reading screen at full-screen scale. Always pair the trigger with a single *commit* haptic so the visual and haptic land together. Do not reach for it on other status transitions — read is the only shelf change that earns a celebration.
- **Animated stat number** — `AnimatedStatNumber` is the canonical way to render a numeric stat that can change in place (profile stats, pages-read counters, deadline pacing). Tweens between values via `animateFloatAsState`, forces tabular figures so digits don't jitter mid-tween, and snaps when the user has disabled system animations (§2.5). Each integer crossing during the tween fires a brief 1dp hairline pulse below the number, tinted with the same content colour as the number itself so the tick reads against any surface (including the primary-filled hero card, where the number is `onPrimary`) — a quiet ledger tick that makes a count feel earned rather than rolled; suppressed under reduced motion. Reach for it whenever a number on screen is bound to live state — pair it with the wavy progress indicator under the Hero stat pattern (§5) so bar and number move as one motion. Raw `Text` for a number that can change should be treated as a bug.
- **Editorial figure / chart** — the family of small, hand-drawn (not library-backed) charts that render a distribution or history inline in the editorial voice, introduced by Profile's "reading life" section. The first three share one colour rule — **monochrome `primary`, never a categorical palette** — because a multi-colour chart would compete with the app's single-accent rule (§2.1); shape (bar height, segment width) carries the data, alpha carries emphasis. The fourth (the demographic breakdown bar) is a deliberate, narrow exception to that rule — see below. This is the flat-bar exception the "wavy progress, always" rule (§2.5/§6) doesn't cover: those bars are **chrome** (a determinate loading/mutation state), these are **data** — a histogram or proportion bar has no "in progress" reading, so it stays a flat `RoundedCornerShape`-clipped `Box`, never the wavy indicator. Reach for these four shapes before hand-rolling a new one:
  - **Peak-annotated bar column** — a `Row` of per-category columns (year, in Profile's case), each a fixed-width `primary` bar sized `minHeight + (value / max) * rangeHeight`, full alpha (1f) on the peak column and ~0.82 alpha on every other column, with the peak value numeral floating above only its own bar and a tabular category label beneath every bar. A hairline `outlineVariant` baseline closes the chart.
  - **Genre proportion stack** — a single full-width `Row` of segments, each `weight`ed to its slice's fraction and filled `primary` at one of five stepping alphas (100/82/64/48/34%) in rank order — the top slice reads solid, each subsequent slice fades a step, and the alphas repeat as the swatch colour in the legend rows beneath (swatch + name + tabular percentage, hairline-separated). Only the reader's **top five genres** are shown, with no "everything else" remainder row: genres overlap (a book carries several), so the percentages are shares of genre *assignments* and an aggregate remainder reads as a whole-of-library share it isn't. `Row` weights normalize, so the bar deliberately still spans the full width even though the five percentages sum to under 100 — it shows proportion *among* the top genres; do not "correct" this with a remainder segment. Profile's gender breakdown reuses this exact shape (up to three slices, ranked Women/Men/Other, `Unknown` excluded and reported separately as a caption count) rather than a shape of its own.
  - **Half-star ratings histogram** — nine bars at half-star resolution; whole-star bars render at full width and 100% alpha, half-star bars at roughly two-thirds that width and ~55% alpha, so the eye reads the whole-star bars as the primary series and the halves as in-between texture. X-axis labels appear only under the whole-star bars.
  - **Demographic breakdown bar** — a fixed **three**-segment Yes/No/Unknown bar, never ranked or resized (unlike the proportion stack above, which drops to fewer segments when there's less data). Yes fills `primary` at full alpha, No `primary` at ~55% alpha; **Unknown is the one deliberate break from this family's monochrome-`primary` rule** — it fills `onSurfaceVariant` at ~22% alpha, a muted non-`primary` neutral, so an untagged share reads as "we don't know" rather than as a third positive category sitting alongside Yes/No. Same hairline-separated swatch + name + tabular-percentage legend as the stacks above, plus a count caption ("Yes 2 · No 5 · Unknown 23 · of 30 authors"). Introduced by Profile's "Who you read" BIPOC and LGBTQ+ breakdowns, each scoped to **every** distinct tagged author — not just the ones with that attribute known — so a large untagged population is always visible rather than folded into a share-of-known percentage that would otherwise skew high.

- **Lazy-item mutation animator** — the canonical wiring for animating add / move / remove on a lazy list when the change is user-triggered. `rememberLazyItemMutationAnimator(keys)` snapshots the initial set of keys on first non-empty composition; the `Modifier.mutationAnimated(scope, animator, itemKey)` extension (overloaded for `LazyItemScope` / `LazyGridItemScope`) returns a `Modifier` (carrying `Modifier.animateItem()` plus a `drawWithContent` accent-bar pulse) that the caller applies to the outermost composable of each lazy item. - **Share card** — `ShareCard` is the single composable that renders any user-facing share artefact (book, hero stat, pulled quote, year-recap slide) into a fixed-aspect editorial composition with a `SOFTCOVER` folio sign-off. Variants are picked by `ShareContent` subtype: book (cover + title + byline + optional rating + optional quote), reading-update (a *personalised* card attributing the book to the reader — see below), stat (`primary`-filled hero with eyebrow + oversize numeral + caption), quote (oversize low-alpha `quoteGlyph` behind italic headline + primary byline), year-recap (eyebrow + display + bulleted highlights), reading-life (a whole-history recap card — see below). Dimensions live in `ShareCardDimensions`; never override them at the call site. The **reading-update** variant (`ReadingUpdateShareContent`) is the centred-stacked personal card: status eyebrow → cover → title → byline → reader identity (circular `RhaydusShimmerImage` avatar + username) → the reader's own tags (when any) → state-specific tail. The reader's tags render as a centred wrapping `FlowRow` of read-only `PillChip`s beneath the identity; **spoiler-flagged user tags are excluded** from the card (a share image is public, so a tag the reader hid from other readers must not leak) — the call-site mapper drops them before handing the names to `ShareCard`. It carries two states, keyed off the user's shelf status, and deliberately omits any recency wording (the user may share long after the fact): **finished** (`Read`) uses the eyebrow "FROM MY SHELF" and shows the reader's rating as read-only `StarRatingInput` gold stars plus their review, rendered through the shared `ReviewDocumentText` so inline spoiler spans are masked as redaction blocks exactly as on the book-detail review (the whole-review render is *not* gated — only the explicitly-marked spans are concealed); **reading** (`Reading`) uses "CURRENTLY READING" and shows a progress label (`page X / Y · NN%`, text only — no bar). The card-content mapping lives at the call site (the review travels as a structured `ReviewDocument`; the rating is the stored 0–5 value handed over untouched; the progress label mirrors the book-detail block — time (`listened / total`) for audiobooks, pages for print — with the percentage derived from the matching unit counts when known and falling back to `UserBookRead.progress`, which is already a 0–100 value); `ShareCard` only renders. It is offered alongside the editorial book card via a `SingleChoiceSegmentedButtonRow` toggle ("My update" / "Book") inside the share sheet, shown only when the book is on the reader's Read or Reading shelf — off-shelf books fall back to the book card with no toggle. Pair with the foundation `CapturableShareCard` + `rememberShareCardCapture(config)` to render the card — Softcover passes `softcoverShareCardCaptureConfig` (gallery album `Softcover`, file-name prefix `softcover`, the app's `FileProvider` authority) and wraps its own public `ShareCard` in `CapturableShareCard`'s generic slot (the card design stays app-side; only the capture plumbing is the foundation's). The foundation `ShareCardCapture` seam (`nl.rhaydus.designsystem.share`, a `commonMain` interface with Android, iOS, and desktop actuals) owns three actions: `capture.saveToGallery(displayName)` writes a PNG into the device gallery (`Pictures/Softcover/` via MediaStore on API 29+, legacy public-Pictures dir + scan on API 26–28; the iOS gallery save is not yet wired); `capture.saveToCache(displayName)` writes a PNG into app cache and returns its identifier; and `capture.share(displayName)` presents the **platform share sheet** for the card image — the OS-level share is part of the capture contract, *not* the calling surface's job (Android builds an `ACTION_SEND` chooser from a `FileProvider content://` URI, iOS presents a `UIActivityViewController`; desktop has no system share sheet, so it copies the PNG to the system clipboard, and its `saveToGallery` opens a native file-save dialog). A surface that just wants to share the card calls `capture.share(...)` and branches on the returned `ShareOutcome` (`Shared` / `Cancelled` / `Failure` — a user-dismissed share sheet is `Cancelled`, treated as a no-op); it never constructs an intent itself. Legacy storage permission (`WRITE_EXTERNAL_STORAGE`, `maxSdkVersion=28`) is requested through `rememberGalleryWritePermissionRequester` — on API 29+ the requester is a synchronous pass-through. Reach for this rather than building a new share image inline; one renderer, one editorial register, one save path. The **reading-life** variant (`ReadingLifeShareContent`, `ShareCardDimensions.ReadingLife` — width 300dp, no fixed height, 560dp minimum, 24dp padding) is the `primary`-filled whole-history recap card: a top masthead (`SOFTCOVER` tracking-wide + italic "A reading life" at 0.7 alpha) over a mini scalloped portrait (a 52dp `MaterialShapes.Cookie12Sided` clip with a 3dp `onPrimary` rim, falling back to initials on a translucent `onPrimary` fill when there is no avatar) and the reader's name, then the "TOTAL PAGES READ" hero numeral (`statHero` scaled to 58sp) with a caption that reads "across N books", a **"WHAT YOU READ MOST" genre ranking** placed directly beneath that hero (see below), a "THE READING YEAR" pages-by-month **ridgeline** (a `Canvas` polyline over its own translucent area fill, both drawn in `onPrimary` at stepping alpha — 0.9 line / 0.22 area — with `JAN`–`DEC` labels beneath; the twelve-value input is padded/truncated so a partial history still renders a flat baseline instead of a malformed chart), and a three-stat footer (avg rating — paired with read-only `StarRatingInput` gold stars per the "gold is rating-stars only" rule, day streak, tracked years). Hairline dividers between the ridgeline/genres/footer sections are `onPrimary` at 0.25 alpha. The **genre ranking** (`ReadingLifeGenre` — name + whole-number percentage, rounded at the call site) is the card's second headline and therefore sits immediately under the pages hero, *above* the reading-year chart: an eyebrow over one row per genre, name left and share right, with the leading genre stepped up to `headlineSmall` at full alpha and the runners-up at `body` / 0.78 alpha, so the top genre is legible at poster distance. The whole section is omitted (with its divider) when the reader has no genres yet. Percentages are shares of genre *assignments* — a book carries several genres — so they intentionally do not sum to 100; never add a total or an "everything else" remainder row to this section. The content model is a plain primitive shape (no `core:profile` dependency, so the card stays self-contained in `core:designsystem`); the profile feature maps its `ReadingLife` domain model onto it at the call site.

- **Drop-cap text** — `DropCapText` renders editorial body prose with a 3-line drop-cap on the first letter, tinted `primary` by default. It lives in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`). The drop-cap font size is `bodyStyle.lineHeight * 3 * 0.92`; the first three lines of body text indent past the cap, and lines four onward resume at full width. Line spacing is uniform across that seam — the cap glyph's own metrics (Fraunces runs taller than the three body lines it spans) only grow the component's total height, never the gap between the indented and full-width runs. Skips leading whitespace and punctuation when picking the letter; falls back to a plain `Text` for empty or letter-less bodies. - **Swipe row actions** — `SwipeRowActions` wraps a list-layout row in a Material 3 `SwipeToDismissBox` and reveals a coloured background as the user drags. Swipe-right (start → end) is the *mark-as-read* action — tertiary container with `ic_bookmark_check` and "Mark as read" copy; suppressed via `allowMarkAsRead = false` when the book is already in Read. Swipe-left (end → start) is the *remove* action — error container with `ic_delete` and "Remove" copy. Reach for it on the `LIST_COMPACT` and `LIST_LARGE` library layouts; never apply it to grid cards.
- **Star rating input** — `StarRatingInput` is the foundation `designsystem-core` interactive personal-rating control (`nl.rhaydus.designsystem.component.StarRatingInput`): a row of five `ic_star_filled` glyphs the user rates against in half-star steps. Empty stars are `onSurfaceVariant` at low alpha by default; the filled portion is the shared `RatingGold` brand colour (the same gold the read-only community/review rating glyphs use — never re-declare the hex at a call site). Partial fills are drawn by clipping the gold glyph to a fraction of its width, so a `4.5` reads as four-and-a-half stars. Tapping a star commits that value (left half → `.5`, right half → whole); dragging horizontally scrubs and fires one `tickle` haptic (§2.5) per half-step crossing. The committed value is reported through `onRatingChange` once per gesture — on tap or on drag release, never mid-drag. Softcover supplies the brand bits at each call site — `starIcon = drawableIconResource(icon = SoftcoverIcon.StarFilled, …)` and `filledColor = RatingGold`. It appears in exactly two places, at two different sizes and two different interaction modes: **inside `VerdictSheet`** (42dp, fully interactive — the *only* place a rating is set or changed) and **inside `VerdictBlock`** (22dp filled / 30dp empty, `enabled = false` with an explicit `emptyColor = outlineVariant` — read-only display; tapping the surrounding card, not the stars, opens the sheet).
- **Verdict sheet** — `VerdictSheet` (`core:designsystem`, `nl.rhaydus.softcover.core.designsystem.presentation.component`) is the combined rating-and-review surface that replaced the old separate rating row and `ReviewEditorBottomSheet`. It is a **shared cross-feature component** — consumed by both `feature/book_detail` (reopened from the book page in `EDIT` context) and `feature/reading` (raised once in `FINISHED` context on a genuine mark-as-read transition, §5 "Verdict prompt") — following the same shared-stateless-component pattern as `ChooseListsBottomSheet` / `UpdateProgressBottomSheet`: each feature hosts it off its own TOAD state and saves through the shared `core:book` `SaveBookVerdictUseCase`. The sheet is a **full-height, three-band layout** — a fixed dismiss header, a scrolling middle, and a pinned action footer — so the primary action is never buried below the fold (the same `fillMaxHeight` + `weight(1f)`-scroll-region + fixed-chrome shape as `EditionBottomSheetSelector`). Band by band: (1) **fixed header** — a right-aligned top-bar dismiss text ("Not now" / "Cancel", following the Tag-editor-sheet's `Done`-in-top-bar precedent) that stays reachable from any scroll position; (2) **scrolling middle** (`weight(1f).verticalScroll`) — a centred 2:3 `EditionImage` jacket (96dp wide, 16dp corners) so the verdict visibly belongs to a book, the canonical `EditorialSectionHeader` (accent bar + eyebrow + italic headline naming the book + an optional description), a 42dp `StarRatingInput`, the **score line + verdict caption** (below), an "In your words" label directly heading a borderless tone-on-tone `BasicTextField` on `surfaceContainerHigh` (no border ring — a deliberate change from the old bordered editor field), then the **review formatting toolbar** + its "Select text…" hint *below* the field (so the label sits against the field it names rather than being pushed off it by the toolbar), and a "Contains spoilers" `Switch` row; (3) **pinned footer** — a hairline `HorizontalDivider` over a full-width filled **Save** and — only in `EDIT` context with an existing review — a text **Delete review**, always visible and (via `imePadding` on the sheet body) parked just above the keyboard while the review is edited. Rating and review are both a **local draft** exactly like the old editor held its buffer: `StarRatingInput`'s `onRatingChange` only updates the draft, and nothing reaches `onSave` until Save is tapped, so leaving with just a rating, just a review, or neither always works — Save is never disabled. The **score line + verdict caption** (`Inter` "YOUR {score} / 10" over an italic `headlineSmall` margin-note caption — one of ten hand-written phrases keyed to the /10 score, e.g. "One that lingers." at 8, falling back to "How was it?" before a rating exists) crossfades with a slight rise on every rating change (`AnimatedContent` keyed on the derived score, ~300ms, `playDecorativeMotion()`-gated). `context: VerdictSheetContext` (`FINISHED` / `EDIT`, `core:designsystem` `presentation.model`) swaps copy only — eyebrow, headline, description, dismiss label, save label — never the anatomy. Reach for it for any surface that lets the reader rate and/or review a book; never reintroduce a rating-only or review-only sheet.
- **Verdict block** — `VerdictBlock` (`core:designsystem`, same package) is the book-page card that replaced the separate "Your rating" row and "Your review" card with one combined surface, on a `surfaceContainer` card (20dp radius). **Empty** (no rating, no review): read-only outline stars (30dp) + an italic invitation ("Rate it and say a few words…") + a quieter hint line. **Filled** (a rating and/or a non-blank review — the two are independent; a rating-only or review-only verdict still renders the filled anatomy, just omitting the piece that has no content): a read-only gold `StarRatingInput` (22dp) + the score line when rated, a hairline `outlineVariant` divider when both a rating and a review are present, the review rendered through `ReviewDocumentText` (up to 8 lines, markdown + spoiler-cover), and a trailing "TAP TO EDIT" hint. An "Edit" text link appears beside the "YOUR VERDICT" eyebrow once any verdict content exists; the whole card is also clickable (`onEditClick`), which the caller wires to open `VerdictSheet` in `EDIT` context. Rating and review are **never edited inline** on the book page — this block is read-only end to end.
- **Review formatting toolbar** — `ReviewFormattingToolbar` (`core:designsystem`, moved alongside `VerdictSheet` — it is only ever used inside that sheet) is the inline bold / italic / spoiler control row for the review editor. It uses the app's pill-chip anatomy (§3.4 / inline filter chip strip): three fully-rounded **word toggles** — `Bold` (rendered bold), `Italic` (rendered italic), `Spoiler` — so the row reads as one deliberate control rather than loose buttons, and the bold/italic chips preview their own effect. Active → `secondaryContainer` / `onSecondaryContainer` (the app's standard selected-chip colours); idle → `surfaceContainer` / `onSurfaceVariant`. Each chip reflects whether the *whole current selection* already carries that mark; with no selection to act on the entire row dims (≈0.45 alpha) and is inert. Reach for it only inside `VerdictSheet`; it is not a generic rich-text bar.
- **Review document text** — `ReviewDocumentText` is the canonical renderer for a stored review (`ReviewDocument`) wherever one is displayed read-only — `VerdictBlock` and community review cards both use it. The base face is **upright** (italic is a per-run mark, not the default voice); bold and italic runs are styled inline; a run marked as a spoiler is hidden under a solid `spoilerCover` block (text drawn transparent over the block) until the reader **taps that span** to reveal it, tracked as transient per-span state. This inline reveal is independent of any whole-review "Show spoiler" gate the caller wraps around it. A tap that does *not* land on a concealed spoiler invokes the optional `onClick` (so the surrounding card still opens on tap). It exposes `maxLines` / `overflow` / `onTextLayout` so callers can drive their own "Show more" affordance. - **Session peek bar** — `SessionPeekBar` is the persistent live-timer bar that rides above the bottom navigation whenever a reading session is active. Anatomy: a `surfaceContainerHigh` rounded bar holding a 32dp `EditionImage` cover thumbnail, the book title (`titleSmall`, single line), a live `H:MM:SS` timer beneath it (or `Paused · …` when paused), then inline pause/resume and stop `IconButton`s. The whole bar is tappable and opens Focus Mode. Pause/resume fires a `select` haptic, stop fires `threshold` (§2.5). It is mounted once, above the nav in both the docked and floating bar styles — never duplicated per screen. - **Barcode scanner** (feature-owned, not a design-system component) — `BarcodeScanner` is the full-bleed camera surface for reading a book's barcode. It lives in **`:feature:scan`** (`presentation/component/`), **not** the design system: camera + ML Kit hardware integration is a feature concern, so the CameraX/ML Kit pipeline and its `androidx.camera.*` / `mlkit-barcode-scanning` dependencies belong to that feature, never to the UI-primitives module. It is documented here only because its chrome reuses two design-system rules: the editorial scrim over the live feed (a `SCANNING` eyebrow + `headlineMedium` instruction in white — **the one place light-on-media copy is allowed**, since the surface is a camera feed, not a theme surface) and a centred rounded viewfinder reticle. Behaviour: it hosts a CameraX `PreviewView` (back camera) feeding the **bundled** ML Kit model (no Google Play Services), constrained to `FORMAT_EAN_13` / `FORMAT_EAN_8` — the formats printed on physical books — and emits the **raw value of the first barcode it reads exactly once** via `onIsbnDetected(raw)`, then stops analysing. For any in-app barcode capture, reuse this feature surface; do not hand-roll a second CameraX/ML Kit pipeline, and do not move it back into the design system.
- **Tag editor sheet** — `TagEditorBottomSheet` is the canonical surface for managing the user's *own* tags on a book (§3.5 modal sheet — editorial header first). Anatomy, pinned top-to-bottom over one scrolling collection:
  1. **Top bar** — the sheet's grabber is `AdaptiveModalSheet`'s own; a right-aligned primary **`Done`** text affordance (dispatched through `LocalModalSheetDismiss`) stays reachable from any scroll position, replacing the old bottom-anchored full-width Done.

- **Choose-lists sheet** — `ChooseListsBottomSheet` is the canonical shared surface for adding/removing one or more books to the user's custom lists (§3.5 modal sheet — editorial header first). It reads as an **editorial index of shelves**, not a checkbox list. Anatomy:
  1. **Header** — composed locally (not `EditorialSectionHeader`, which can't tint a substring of its headline), following the Tag-editor-sheet precedent: accent bar + `LISTS` eyebrow, an italic headline naming the act — "Shelve **{book title}**" (single, the title in a `primary` `AnnotatedString` span) or "Shelve **{n} books**" (bulk, `bookTitle` left `null`) — and an italic description (single: "Tap a list to file it here — tap a filled one to take it off. The whole row is the tap target; the pill is display-only.
  3. **Create row** — "Create a new list" (unchanged `onCreateNewListClick`), restyled as a quiet dot row: a 26×26 `surfaceContainerHigh` circle holding a `primary` "+", then the label in `primary`. No hairline card.

  The sheet is a **dumb renderer** — every toggle and the create action are reported through callbacks; the caller owns the `AddBookToListUseCase` / `RemoveBookFromListUseCase` writes and decides whether to stay open for consecutive adds. Reach for it for any add-to-list affordance; do not build a per-screen list picker.
- **Change edition sheet** — `EditionBottomSheetSelector` is the **feature-local** (`feature/book_detail`, not shared — only Book Detail offers an edition switch) surface for picking which edition of a book the reader tracks. Anatomy:
  1. **Header** — composed locally like the Choose-lists sheet: accent bar + `EDITIONS` eyebrow, italic "Change edition" headline, an italic description reading "{book title} · {author}" (`currentEdition.authorString`; the "· author" suffix drops when blank), and a trailing 56×84 `EditionImage` of `currentEdition`.
  2. **Search** — the house `EditorialSearchField` (§4), not a boxed Material `OutlinedTextField` — tone-on-tone, full pill radius, leading search glyph, trailing clear-only ×, placeholder "Search by ISBN or publisher".
  3. **Count label** — "{n} EDITIONS", uppercase `eyebrowSmall`/Inter, `onSurfaceVariant`.
  4. **Edition cards** (the **edition-difference card** — reusable anatomy for any "pick among near-identical items" list) — one `LazyColumn` row per edition, **differences-first**: a 44×66 `EditionImage`, then a leading **format icon + label** row (the format is the differentiator, so it leads — `readingFormat` maps to a glyph: audiobook → headset, e-book → the library-books glyph (no dedicated ebook glyph exists), physical/both → the menu-book glyph; the label is `edition.format` when set, else `readingFormat.label`), a single **tabular** meta line (`publisher · year · pages`, pages swapped for a duration on an audiobook via the foundation `toHoursMinutesSeconds()` — never hand-rolled — with unknown parts dropped), an **ISBN whisper** demoted to `onSurfaceVariant` at 70% alpha, and — when owned — "You own this edition" in `primary` with a leading bag glyph. Card state: `selected` → `surfaceContainerLow` fill + a filled `primary`/`onPrimary` check circle trailing the format row; **owned** or **selected** → a 1.5dp `primary` inset outline (both read as "this edition matters"); the **currently-tracked** edition (`edition.id == currentEdition.id`, when not itself selected) → a quiet `surfaceContainerHigh` "TRACKING NOW" chip instead of the check. Tapping a card sets local `selectedEdition` state (unchanged — not part of the TOAD contract).
  5. **Confirm foot** — a full-width filled `RhaydusButton`, label **"Track this edition"** (edition-agnostic — not "Confirm edition"), enabled once a different edition than `currentEdition` is selected and not loading. Loading and empty-search states are unchanged (house wavy indicator, never a circular spinner; "No editions match your search" in `body`/`onSurfaceVariant`).

  Reach for the edition-difference card anatomy for any other "pick the right variant" list; do not reuse `EditionBottomSheetSelector` itself outside Book Detail.
- **Connectivity chrome** — `ConnectivityBanner` (a transient "you're offline" banner shown by the app shell) and the `OfflineGuard` helpers `rememberIsOnline()` + `OfflineScreenContent` (a full-surface empty-state for a screen whose content cannot load offline) are **shared `core/presentation/component`s**, consumed by the shell (`RootScreen`) and any feature screen that must degrade offline (e.g. `explore`, `book_detail`). They read network availability through the `core:domain/connectivity` contracts — no feature owns them. Reach for `OfflineScreenContent` for any "needs the network" empty state; do not hand-roll a per-screen offline placeholder.
- **Active reading session** — `ActiveSessionController` is the **app-scoped single source of truth** for the running reading session (`core/presentation/session`), exposed as a `StateFlow` and consumed by the peek bar, Focus Mode, the reading tab, and the lock-screen foreground service. It is a shared `core` contract (the interface lives in `core/presentation/session`; its impl is in `:orchestration`) — not a feature internal — because ≥2 surfaces drive it. It launches the platform foreground service through the `ReadingSessionLauncher` **contract** (impl in `feature/session`), so core never depends on the service. `SessionPeekBar` and `FocusModeScreen` are the feature-owned surfaces that render its state.
- **Personal review section** — the book-detail entry point into the review editor, in the Yours lens. A bar-less in-flow `YOUR REVIEW` label (§2.3's no-bar register) with a trailing primary-coloured **`Edit`** affordance (shown only once a review exists) heads a single tappable card: `surfaceContainerHigh` / **"Write a few words…"** editorial prompt when no review exists, or a `surfaceContainer`, 20dp-radius, 18dp-padded card holding the review rendered via `ReviewDocumentText` (upright editorial body), clipped to `REVIEW_COLLAPSED_LINES`, with a quiet "contains spoilers" footnote when the whole-review flag is set. Tapping anywhere on the card — including the rendered text, except a concealed spoiler span — opens the review editor sheet seeded with the current structured review. It sits directly beneath the your-tags section on the Read shelf so a reader's rating and words live together. The review rides on the cached `user_book` row (as a structured `review_slate`), so it arrives with the book and reflects edits made elsewhere — no separate load, no skeleton, no flash.
- **Settings menu row** — the borderless, hairline-separated row anatomy for a menu of navigational entries (the mobile Settings screen's Account / Personalisation groups). Anatomy: a top `outlineVariant` hairline drawn on **every** row including the first (so a run of rows reads as one continuous hairline list, never a boxed `Surface`/card), a 42dp `surfaceContainerHigh` icon tile (12dp radius) holding a `primary`-tinted glyph, an Inter `titleMedium` label (never italic) over a one-line italic Fraunces `bodySmall` gloss, and a demoted `onSurfaceVariant` trailing chevron. Pressing washes the row to `surfaceContainer` (an `animateColorAsState` tied to the row's own `InteractionSource`, gated by `playDecorativeMotion()`) — the row's only container tint; it never becomes a full `Surface` background. The editorial accent-bar + eyebrow ceremony belongs to the group header (`EditorialSectionHeader`) once per group, never per row. Reach for this anatomy for any settings-style menu list; it supersedes the earlier boxed `SettingsGroup` treatment entirely — `SettingsGroup` / `SettingsRowDivider` are retired: their one remaining consumer, the reorderable Library-tabs list, has moved to its own flat row anatomy ("Library tabs reorderable row", §5).
- **Update highlight card** — the Settings screen's `primaryContainer` editorial highlight (`AppUpdateSection`), shown only while an app update is not `Idle`. This is a **second, distinct tinted-card convention from the primary-filled hero stat card** (§2.1): where the hero stat fills solid `primary` and is capped at one per scrollable region, this card fills `primaryContainer` / `onPrimaryContainer` (radius 12dp) and is reserved for this one system-status callout. Anatomy: a hand-composed accent-bar + all-caps Inter eyebrow (not `EditorialSectionHeader`, since its headline is fixed to `onSurface` and this card needs `onPrimaryContainer`), an italic Fraunces headline, and a state body — a fully-rounded `Surface(onClick, shape = percent(50))` pill action (`primary` / `onPrimary`, the same anatomy as `PillChip` and the Library control-line pills) for Available/Downloaded/Failed, or an **indeterminate** `LinearWavyProgressIndicator` (`primary` stroke / `outlineVariant` track, no percentage) while Downloading — the client has no reliable version string or download percentage to show, so headlines and copy are deliberately version-less ("A new version is ready", never "Version 3.2.0"). No badge, no chevron, no whole-card click — the pill (or the absence of one, while downloading) is the only affordance.
