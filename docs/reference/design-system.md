# Design System
The visual and interaction language for Softcover. This document is purely descriptive — it does not point at code. When a screen is being designed or redesigned, a contributor should be able to read this and know how the surface should look and behave without consulting other screens.

> **Maintenance rule.** Any change that introduces, retires, or alters a foundation, component, or pattern in this system must update this file in the same change. If the doc and the code disagree, the code is wrong, the doc is wrong, or both — none of those is acceptable to merge.

---

## 1. Tone

The system is **editorial**: it borrows from print magazines and book covers rather than from utility dashboards. Surfaces feel like spreads. Type does heavy lifting; chrome is restrained. Italic display faces and a single primary accent carry character. Decoration is sparing — a thin accent bar, a quote glyph, a wavy progress indicator — and always serves a hierarchy decision, not ornament for its own sake.

The reader is the protagonist. Their books, progress, and stats are foregrounded; app affordances retreat.

## 2. Foundations

### 2.1 Color

Color is sourced from the Material 3 expressive scheme; this section defines the *roles* those tokens play in this app.

- **Primary.** The accent. Used for emphasis on text and chrome (eyebrows, key stats, the leading mark of a section, progress indicators, cursors, active toggle states, a button's filled style), and — deliberately — as the **surface fill of a hero stat card**: the page-opening stat tile (e.g. the profile screen's pages-read hero). At most one primary-filled card per scrollable region. Inside such a card the content colour is `onPrimary`; demoted text drops to `onPrimary` at ~0.75 alpha; the divider drops to `onPrimary` at ~0.25 alpha; if the card needs a call-to-action it steps down a tier (elevated or tonal) so it doesn't disappear into the surface. This treatment is reserved for stat heroes — cards built around imagery (covers, photos) keep a `surfaceContainer*` shade so the imagery, not the chrome, carries the colour. Beyond the stat hero, primary is **not** a background colour — ordinary cards, tiles, sections, and grouped regions use page background or a `surfaceContainer*` shade.
- **On-surface / on-background.** Body and headline copy. Default for almost all readable type.
- **On-surface-variant.** Demoted copy: suffixes, captions, secondary metadata, inactive labels. Use to push information back without losing legibility.
- **Surface / background.** Page canvas. Plain.
- **Surface-container, surface-container-high, surface-container-highest.** Elevated tiles, cards, and grouped sections. Step up the container shade to express grouping or focus, not depth in pixels — elevation is communicated by tone, not by drop shadows.
- **Surface-container-lowest.** Reserved for modal sheets and overlays that sit *above* the page rather than within it.
- **Outline / outline-variant.** Hairline dividers and the rare bordered control. Avoid dense rule lines; prefer whitespace and tone changes.
- **Inverse-primary.** Notification dots and small attention markers on chrome.
- **Error / on-error.** Destructive and validation states only.
- **Rating gold (`RatingGold`).** A single warm gold reserved exclusively for rating-star glyphs — both the read-only community/review rating and the interactive personal rating control. It sits *outside* the Material scheme (and the dynamic-color override) because the gold reads identically in light and dark and is a deliberate "rating" signal rather than a theme role. Never use it for anything that isn't a rating star, and never re-declare the hex at a call site.
- **Spoiler redaction (`ColorScheme.spoilerEditorHighlight` / `ColorScheme.spoilerCover`).** The treatment for inline spoiler runs inside a review, both derived from `onSurfaceVariant` so they track light/dark. The two roles are deliberately different by surface: in the **review editor** a spoiler run gets the translucent `spoilerEditorHighlight` wash (the author must keep reading their own words), while on **display** the run is hidden under the near-solid `spoilerCover` block until the reader taps to reveal it. Use these only for the per-run spoiler mark; the whole-review spoiler gate is a separate "Show spoiler" affordance (§5), not a colour role.

Dynamic color (Android 12+ Material You) is supported but **off by default**. The editorial scheme is the canonical look; dynamic color is an opt-in personalisation, not the design.

### 2.2 Typography

Two type families carry the system, split by voice. Both are bundled with the app (as Compose Multiplatform font resources) so the branded type renders identically on every platform — Android, iOS, and desktop:

- **Fraunces** — the editorial serif. A serif face with true italics; carries every role where the editorial voice should be heard: page titles, display headlines, italic headlines, italic body prose, hero stats, and the decorative quote glyph. Stats use Fraunces with tabular figures so digits don't jitter when numbers animate.
- **Inter** — the chrome sans. Carries everything that should retreat: eyebrows (all-caps with wide tracking), card and list titles, Material component internals (top-bar titles, button labels, navigation labels, dropdown items), and any utility label. Inter is roman in this system; if a chrome surface needs italic, that is a sign the role belongs in the editorial scale instead.

Two parallel scales coexist:

- **Material typography** — the standard body/title/label scale used inside off-the-shelf Material 3 components. Components consume this implicitly; do not override it for component internals.
- **Editorial typography** — a project-specific scale, accessed alongside Material typography, used for any text the *screen itself* composes. Roles below.

| Role            | Where it goes                                                                 | Character                          |
| --------------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| `eyebrow`       | All-caps section labels, kicker over a headline, accent over a hero stat     | Wide letter-spacing, semibold      |
| `eyebrowSmall`  | Same role, when packed inside cards/rows                                     | As above, tighter                  |
| `pageTitle`     | The screen's primary title rendered *inside* the scrolling page (not the top-bar slot — that uses Material `titleLarge`). Reach for it on root screens whose top bar is transparent or absent. | Roman, semibold, large |
| `display`       | Section headlines that follow an eyebrow                                     | Italic, semibold, expressive       |
| `headlineMedium` / `headlineSmall` | Subsection or modal headlines                                  | Italic, semibold                   |
| `titleLarge` / `titleMedium` / `titleSmall` | Card titles, list item titles, grouped row headers       | Roman, semibold                    |
| `bodyLarge` / `body` / `bodySmall` | Running prose, descriptions, captions                            | Italic                             |
| `statHero`      | The single largest number on a screen (e.g. a hero count)                    | Italic, semibold, oversize         |
| `statLarge`     | Editable hero numbers (input fields styled as stats)                          | Italic, semibold                   |
| `quoteGlyph`    | Decorative oversized quotation mark — used either behind an actual quote block or as an editorial flourish in an empty state. Tinted `onSurfaceVariant` at low alpha. | Display face, very large, low alpha |

Italic is a deliberate signal of editorial voice; it is reserved for display, headlines, body prose, and stats. Roman is reserved for page titles, card/list titles, and component chrome — places where italic would feel decorative rather than deliberate.

Never inline an ad-hoc `TextStyle`; pick the closest editorial or Material role and `.copy(...)` only when a documented exception requires it (e.g. tinting `quoteGlyph` with a low alpha).

### 2.3 Shape & elevation

- **Corners.** Small radii on cards and tiles; medium on buttons (Material defaults via expressive theme); larger, fully-rounded for the active state of toggle buttons. Cover art uses a subtle radius to hint at a printed object without softening it into a sticker.
- **Elevation.** Tonal, not shadowed. Surface-container shades replace drop shadows for grouping. The one exception is book covers, which carry a slight shadow to read as physical objects on the page.
- **Accent bar.** A short, primary-coloured bar in two sizes, picked by the role of the eyebrow it leads:
  - **Section bar — 32×4 dp.** The "this is a section / this is a sheet" mark. Sits in the page gutter (not inside a card) and precedes a full-size `eyebrow` + display/headline pair. Used by sheet headers, settings section headers, and any top-level region introduction.
  - **Inline bar — 20×1 dp hairline.** The smaller-scale variant for an eyebrow living *inside* a card, hero region, or subcomponent. Always paired with `eyebrowSmall`, never with the full `eyebrow`. Used on featured cards (Reading), page-title accents (Library), and inline status callouts (Book detail).
  Never mix sizes: a full `eyebrow` always gets the 32×4 bar; an `eyebrowSmall` gets either the 20×1 hairline or no bar at all.

### 2.4 Spacing

Spacing is rhythmic, not formulaic. The recurring values are:

- **4 / 8** dp — tight inline gaps (icon-to-label, badge offsets).
- **12 / 16** dp — within-component padding, label-to-control gaps.
- **20 / 24** dp — page horizontal padding, gap between a card's image and its text block.
- **28 / 32** dp — gap between distinct content blocks inside a sheet or hero region.
- **40 / 48** dp — gap between major page sections.

Sections always breathe. Two adjacent eyebrow/headline pairs without a generous gap between them is a layout bug.

### 2.5 Motion

- Use the Material **expressive** motion scheme; do not hand-author durations or easings unless animating a custom property the scheme cannot express.
- **Press feedback.** Tappable cards, primary (filled) buttons, and ripple-less hero surfaces scale to ~0.97 while pressed and ease back to 1f on release. The scale rides an `InteractionSource` so it lines up with the platform's pressed-state ticks; it is wired through `Modifier.pressScale` (a press-driven `graphicsLayer` scale) or its `Modifier.pressScaleClickable` convenience (which bundles a ripple-less `clickable`). Suppressed under reduced motion (§2.5 gate). Press scale is the *only* indication on ripple-less surfaces — never strip the ripple from a card or hero without adding the scale, or the surface loses its press feedback entirely. Tonal/outlined/text/elevated buttons keep the Material ripple + pressed-shape morph and do not stack scale on top; a single button surface only carries one press treatment.
- **Press haptics.** A *commit* haptic fires only on commit-class actions (mark-as-read, save, confirm) — never on navigation taps (tapping a book card to open detail, tapping a row to push a sub-page). Press scale is purely visual; it never implies a haptic.
- **Desktop hover & cursor.** Pointer-only affordances that are inert on touch (no pointer device) and surface on desktop, where the bespoke `jvmMain` screen layouts apply them. Two shared modifiers carry them: `Modifier.pointerHandCursor()` puts the platform "clickable" hand cursor on a surface while the pointer is over it; `Modifier.hoverHighlight(interactionSource, shape, color)` cross-fades a subtle overlay (default: a low-alpha `onSurface` wash) over a surface while hovered — the hover sibling of `pressScale`, sharing the same `InteractionSource` as the surface's `clickable`/`hoverable`. Reach for hover highlight on rows, cards, and list/grid cells that a desktop user would expect to light up under the pointer; pair it with the hand cursor on the same surface. Do not author bespoke hover tints or cursor swaps per screen — these two modifiers are the only way to wire desktop hover affordances. They are decorative-only (never the sole indication of state) and carry no haptic.
- **Desktop tooltip.** Icon-only controls (back, close, refresh, scan, overflow, the control-strip layout/rearrange toggles, the session peek bar's transport buttons) carry only a `contentDescription` — invisible to a sighted pointer user, so the hover state promises a label that never arrives. The shared `DesktopTooltip(text) { control }` wraps such a control in a hover tooltip: on desktop it renders a small editorial surface (`surfaceContainerHighest`, 8dp radius, Inter `labelMedium`) after a short hover delay; on touch it is a **pure pass-through** (no wrapping layout node), so a shared composable wrapped in it is byte-identical on Android and iOS. It is a `commonMain` expect (`:core:designsystem`) with a jvm `actual` (Compose Desktop's hover-triggered `TooltipArea`, *not* Material3's long-press `TooltipBox`) and a mobile pass-through `actual` — the same seam shape as `pointerHandCursor()`. Pass the human-readable label as `text` (the icon's `contentDescription` stays the accessibility label); it is decorative-only and carries no haptic. Reach for it on every icon-only desktop control — including ones living in shared `commonMain` components — and never hand-roll a per-screen tooltip. Controls that already show a text label (a `RhaydusButton`, a labelled sidebar row) do not get one.
- **Desktop scrollbar.** Long desktop lists and grids carry a persistent vertical scrollbar — mouse-wheel scrolling has no fling or edge-glow, so the scrollbar is how a desktop user reads and grabs their position. The shared `DesktopVerticalScrollbar(gridState, modifier)` (jvm-only, `:core:designsystem`) wraps Compose Desktop's `VerticalScrollbar` + `rememberScrollbarAdapter`; overlay it on the trailing edge of the grid's `Box`, driven by the same `LazyGridState` the grid scrolls on. A `LazyListState` overload covers uniform-height `LazyColumn` shelves; a `ScrollState` overload covers non-lazy `verticalScroll` content. Prefer the `ScrollState` overload when the content is short and its items vary wildly in height (e.g. the desktop Reading list, where a tall featured card sits above short rows): a lazy adapter only *estimates* total height from the average measured-item size, so the thumb jumps as the tall item scrolls out — a fully-measured `ScrollState` reports the exact extent and keeps the thumb stable. The thumb is keyed to the theme's `onSurface` (Compose Desktop's default thumb is near-black and invisible on the dark editorial surfaces), brightening on hover. Touch platforms get no scrollbar (the fling + overscroll glow is the affordance), so it never appears in a `mobileMain` layout. This is the desktop counterpart to — not a contradiction of — the carousel "no scrollbar" rule (§4): book *carousels* still lean on the partially-clipped edge card as their overflow cue; the scrollbar is for the long *vertical* shelves a desktop window makes tall.
- **Desktop back strip.** A pushed desktop screen carries a static `DesktopBackStrip(onNavigateBack, backIcon)` (jvm-only, foundation `designsystem-core`) in place of a scroll-collapsing top bar — a single hand-cursored back `IconButton` in the leading gutter, over the screen's opaque background. The strip is brand-agnostic, so the app passes its own back-arrow as a `RhaydusIconResource` (`drawableIconResource(contentDescription = …, icon = SoftcoverIcon.ArrowBack)`). It is the desktop counterpart to the `SoftcoverTopBar` back affordance a `mobileMain` layout uses; never hand-roll a per-screen back row. Used by the desktop Profile, Create List, and Barcode Scanner layouts. Touch platforms get `SoftcoverTopBar` instead, so it never appears in a `mobileMain` layout.
- **Desktop selection: right-click + modifier-click.** Touch enters multi-select via long-press, which is invisible to a pointer user — so desktop adds the two native pointer gestures. **Right-click** on a book cover/row opens a context menu (`DesktopContextMenu`, §4) — Open, Select / Add-to-selection, and the per-book operations that reuse the bulk pipeline (Mark as read, Add to list…, Remove). **Ctrl/Cmd-click** toggles a cover's selection (entering selection mode if needed) and **Shift-click** range-selects the visible span to the last-clicked anchor, both via `Modifier.platformModifierClick(onCtrlClick, onShiftClick)` — a jvm interceptor that consumes the press in the pointer Initial pass only when a modifier is held, so a plain click still opens the book and the modifier-click is preempted with no double-fire. Both seams are pure pass-throughs on touch (the long-press path is untouched), so the shared library cells stay byte-identical on Android and iOS. Reach for them on any desktop list/grid that supports selection; the per-book context actions reuse the existing bulk actions targeted at a single book (the action carries an explicit id set) rather than a parallel single-item write path.
- **Desktop Esc-to-dismiss.** Pressing **Esc** closes whatever desktop overlay sits over the page — the baseline desktop reflex. The expanded-width modal panel (`AdaptiveModalSheet`'s `Dialog` form, §3.5) gets this for free: Compose Desktop maps a `Dialog`'s `dismissOnBackPress` to Esc. The in-app surfaces that are *not* a `Dialog`/`Popup` — Focus Mode, the full-screen cover viewer, and Library bulk-select / Rearrange mode — wire it explicitly through the jvm-only `Modifier.dismissOnEscape(enabled, onDismiss)` (`:core:designsystem`): while enabled it takes focus once and catches Esc in the *preview* (tunnelling) phase, so it fires even when a descendant text field holds focus, and it is a no-op (never grabbing focus) when disabled — so it can be gated on a transient mode without disturbing normal focus. It is the desktop sibling of the `mobileMain` `BackHandler`; keep both (Esc on desktop, back on touch). Reach for it on any in-app desktop overlay; do not hand-roll per-screen key handling. Accelerator shortcuts beyond Esc (e.g. ⌘F, ⌘,) and a native menu bar are deliberately out of scope for now.
- **Tap-to-dismiss scrims are pointer-only.** A full-screen "tap empty space to clear focus / dismiss" scrim must be wired with `Modifier.pointerInput { detectTapGestures { … } }`, **never** `Modifier.clickable` / `noRippleClickable`. On desktop a `clickable` also binds **Spacebar/Enter** as activation keys, so a focused text field whose space key bubbles up (it isn't fully consumed) lands on the scrim and clears its own focus mid-typing — every field in the app breaks on the spacebar. `detectTapGestures` reacts to pointer taps only (no key binding, not focusable), preserving tap-to-dismiss on touch and desktop without the side effect, and it keeps a phantom full-screen clickable out of the accessibility tree. Reserve `clickable` for surfaces that genuinely *should* activate on Space/Enter (buttons, rows, cards).
- Progress is shown with the wavy progress indicator — flat bars are reserved for chrome (top-bar scrim) and never carry semantic progress.
- Numeric progress animates between values rather than snapping.
- Sheets enter and dismiss from the bottom; overlays cross-fade.
- **Tab-root swap.** Switching between the four bottom-bar roots plays a 200ms cross-fade with a 12dp upward drift on the incoming tab — never a hard cut, never a horizontal slide (which would imply spatial relation between unrelated roots). Per-tab `rememberSaveable` state survives the swap via a shared `SaveableStateHolder` keyed by tab key. Suppressed under reduced motion (§2.5 gate) — in that case the previous instant swap is used. Sub-screens pushed onto a tab's stack continue to use the standard `ScreenTransition` (currently `None`); this rule applies only to the root-tab swap.
- **Mark-as-read commit choreography.** When a book transitions to the Read shelf via a user action (chip tap on book detail, "Mark as Read" menu item on the reading screen, or progress reaching 100%) the surface plays a ~800–1000ms burst: a primary-color particle burst (`MarkAsReadBurst`, §4), the chip's check-icon punches with a left-to-right reveal, the section-label accent bar pulses, and a single *commit* haptic fires. No other shelf transition (Want-to-read, Reading, DNF) earns the celebration — only Read. On the Reading screen specifically, the celebrated row also performs a "slide to shelf" follow-through: ~320ms downward translate (~96dp) + fade, played before the screen-model action dispatches; the Library bottom-bar icon pulses once in parallel (180ms peak to 1.22× scale, 240ms settle) via `BottomBarPulseManager.pulseLibrary()`, so the eye is led from the source row to the shelf where the book just landed. Both the slide and the pulse are suppressed under reduced motion (the action dispatches synchronously instead).
- **Mutation-rejection shake.** When an optimistic mutation rolls back, the affected card/row plays a single horizontal shake: 6dp amplitude, 80ms each half-period, 3 cycles, returning to centre. The card's eyebrow slot also swaps to the error role with a "Couldn't save — tap to retry" label for the duration of the failed state. Use the shared `Modifier.shakeOnError` for this — never hand-roll the animation.
- **Lazy-list add/remove animation.** Only user-triggered list mutations animate; initial load, background refresh, and pagination tail jump as today. Removals fade out and neighbours slide into the vacated space; additions fade in and play a brief 20×1 dp accent-bar pulse (§2.3 inline-bar hairline) at the top edge of the inserted item. The shared `Modifier.mutationAnimated` extension (§4) is the only way to wire this up — do not hand-roll `animateItem` per call site, and never wrap the item in a `Box` to host the modifier (the wrapper layout node causes stale lazy-item measurements).
- **Staggered entry on first composition.** Carousel and list items that compose during the initial screen-entry window play a brief upward translate (~8dp) + fade in, delayed by ~60ms per index. Items composed after the window (scrolled into view, swapped in by a background refresh, mutated in later) render statically — this is a one-shot welcome moment, never an "animate on scroll" effect. Wire it via the shared `rememberStaggeredEntryCoordinator` + `Modifier.staggeredEntry(coordinator, index)` (§4); compose it onto the item modifier alongside the mutation animator when both apply. Suppressed when system animations are disabled.
- **Cover-to-detail morph.** A tapped book cover on any source surface (library, explore carousels, reading) morphs into the book-detail hero cover via `Modifier.sharedBounds`. The morph is opt-in: pass `sharedTransitionKey = bookCoverTransitionKey(editionId, bookId)` to `EditionImage` at both source and destination. Both call sites must derive the same key — prefer edition id, fall back to book id. The destination paints the cover immediately from a `BookInitialCover` carried through navigation, so the morph never lands on an empty hero. The shared scopes (`LocalSharedTransitionScope`, `LocalNavAnimatedVisibilityScope`) are provided by the navigator shim in `RootScreen`; non-morphed pushes look identical to before. Do not apply the key to decorative `EditionImage` usages (e.g. blurred backdrops, full-screen cover viewer) — only to the tappable source cover and its detail hero.

### 2.6 Iconography

- Material outline icons, stroke weight consistent across the app. Never mix filled and outlined icon families on the same surface.
- Icon-only controls always carry a content description.
- Icon size scales with the control's size token (XS → XL); icons embedded in body type sit on the type baseline at a size proportional to the surrounding text.

**Icon tokens.** Icons are addressed through two design-system types, never through the platform resource system:

- `SoftcoverIcon` (`core/designsystem/presentation/icon/`) — the typed catalog of the bundled vector drawables (`SoftcoverIcon.Search`, `.Close`, …), backed by Compose Multiplatform resources (the underlying `Res` is internal to the module, so it resolves identically on Android and iOS).
- `RhaydusIconResource` (foundation `designsystem-core`, `nl.rhaydus.designsystem.icon`) — the icon *token* passed to components and drawn at call sites. It is a sealed type carrying a `contentDescription` plus one of: `Drawable(resource: DrawableResource)` (a catalog vector), `Vector(vector: ImageVector)`, or `Custom(painter: Painter)`. Build the catalog-vector case from a `SoftcoverIcon` via the app bridge `drawableIconResource(contentDescription, icon)` (`core/designsystem/presentation/icon/`), which resolves the catalog's internal `DrawableResource` so call sites still pass the typed `SoftcoverIcon` and the CMP resource stays module-internal. Always draw through the token — `Icon(painter = token.getIconPainter(), contentDescription = token.contentDescription, …)` — so the content description always travels with the icon and the catalog-vector / arbitrary-painter distinction stays meaningful. Do **not** reach for a raw `painterResource`/`SoftcoverIcon`-to-`Painter` shortcut at a draw site, and components that accept an icon take a `RhaydusIconResource`, not a bare `SoftcoverIcon`.
- A handful of icons that feed **Android-only** sinks a Compose painter can't reach — the foreground-service notification (`ic_reading`/`ic_play`/`ic_pause`/`ic_stop`/`ic_edit`) and the app's notification appearance (`ic_bookmark`) — are intentionally kept as Android `R.drawable` resources in `core:designsystem`'s `androidMain` as well; everything Compose goes through `SoftcoverIcon`.

**Illustrations.** Full-bleed editorial artwork (onboarding intro panels, empty states) is addressed the same way — through a design-system catalog, never the platform resource system:

- `SoftcoverIllustration` (`core/designsystem/presentation/illustration/`) — the typed catalog of bundled illustration drawables (`SoftcoverIllustration.Writing`, `.SignUp`, …), backed by Compose Multiplatform resources with the underlying `Res` kept internal to the module, so the artwork resolves identically on Android and iOS. Draw through its `@Composable painter()` accessor — `Image(painter = illustration.painter(), contentDescription = …)` — and pass the contextual content description at the call site; never reach for a raw `painterResource` at the draw site.

### 2.7 Window size & breakpoints

The app runs on phones, tablets, foldables, and resizable desktop windows, so every surface adapts to the width it is given. Width is bucketed into three classes, and these are the **only** sanctioned breakpoints — a screen reads the class, it never hardcodes a dp threshold:

- **Compact — `< 600dp`.** Phones in portrait, narrow windows. The canonical bottom-bar shell.
- **Medium — `600–840dp`.** Large phones in landscape, small tablets, medium desktop windows. The navigation rail replaces the bottom bar.
- **Expanded — `>= 840dp`.** Tablets, unfolded foldables, desktop windows. A permanent editorial sidebar replaces the rail, and root list surfaces gain a side-by-side detail (the **list–detail two-pane** pattern, §5).

The class is read through `rememberWindowSizeClass()` (foundation `designsystem-core`, `nl.rhaydus.designsystem.layout`), which recomputes as the window resizes or a device folds. It exposes the bucketed `widthClass` plus the measured `widthDp` / `heightDp` for the rare *continuous* sizing decision (a hero whose height tracks the viewport) — reach for the class first; fall back to the measured value only when a discrete bucket genuinely can't express the layout. The navigation chrome progression is fixed: **bottom bar (compact) → rail (medium) → sidebar (expanded)**; the docked/floating bottom-bar preference (§4) only applies in compact.

## 3. Layout primitives

### 3.1 Page scaffold

A page has, top-to-bottom: optional top app bar, scrolling content with horizontal padding consistent for the whole page, and bottom navigation (when on a tab root). The bottom of scrolling content reserves padding equal to the bottom bar's footprint so the last item is never occluded.

Top bars are either a plain title bar (centered or start-aligned title, optional subtitle, optional back, optional trailing actions) or a search bar (text field with leading search/loading state and trailing clear). Both are sourced from the shared top-bar components — no screen rolls its own.

**Root tabs prefer an in-page editorial title over a chrome title.** Reach for `SoftcoverTopBar` with a plain `title` only when the screen needs back navigation or trailing icon actions — i.e. on sub-screens pushed into the stack (settings sub-pages, profile, book detail). On a root tab, the screen's identity is rendered *inside* the scroll using the `pageTitle` editorial role (optionally paired with a body subtitle), so it shares the editorial scale with the section headers below it. The Material `titleLarge` chrome title reads as system chrome and clashes with the editorial section rhythm that follows. Library and Settings both follow this rule; Explore is title-less by design (its search bar is the chrome).

### 3.2 Section rhythm

A content section is composed of:

1. **Eyebrow** — short all-caps label in primary colour.
2. **Headline** — italic display headline directly underneath the eyebrow, on-surface colour.
3. **Body** — the section's content: a horizontal carousel, a vertical list, a grid, or a single block.
4. Generous vertical gap before the next section.

This is the canonical pattern. Anywhere a screen needs to introduce a region of content, it uses this triplet — the eyebrow gives the editorial label, the headline gives the human-readable title, and the body delivers.

### 3.3 Hero region

A hero region opens a screen with a single dominant element: a stat, a quote, or a featured cover. Hero text uses `statHero`, `display`, or a quote pattern (oversized low-alpha `quoteGlyph` behind italic headline). Hero regions sit on the page surface, not on a container — they are part of the page, not a tile within it.

### 3.4 Carousels and cards

Horizontal carousels are the default for collections of books. Cards inside a carousel are fixed-width and fixed-height. Optional rows inside a card (rating, badge, secondary line) reserve their height even when empty so cards do not jump as data resolves.

Horizontal carousels do not paint an explicit overflow affordance (no edge bar, no chevron, no fade). The rightmost card sitting partially clipped against the screen edge — paired with the standard 24dp content padding so it never butts flush — is itself the "there's more" cue. Do not reintroduce a page-edge hint, scrollbar, or page indicator on book carousels.

Card anatomy (top-to-bottom):

1. Cover image (book proportions, subtle radius and shadow).
2. Title in `titleMedium` or `titleSmall`, max two lines.
3. Optional metadata strip in `eyebrowSmall` or `bodySmall`, on-surface-variant.
4. Optional trailing accent (rating, progress fragment) in primary colour.

Vertical lists use the same anatomy laid horizontally: cover at the leading edge, text block taking the remaining width.

### 3.5 Modal sheets

Modal bottom sheets open in a fully-expanded state on `surface-container-lowest`. The first element inside is always the canonical header pattern — accent bar, eyebrow, headline (and optional editorial description line) — followed by the sheet's body content. Sheets handle their own dismissal; they never require a custom close button.

**This rule has no exemptions.** Every modal sheet — pickers, action sheets, progress sheets, blocking loaders that happen to be implemented as a sheet — opens with the editorial header. A sheet's job is to feel like a small editorial spread, not like a Material dialog. Material `titleLarge` / `bodyMedium` headers signal "system chrome" and read as a regression; reach for `eyebrow` + `display`/`headlineMedium` + `body` instead. If a sheet's content is so transient that an editorial header feels theatrical, that is a signal it should be a `Dialog` (an unobtrusive overlay), not a sheet.

**Worked example — blocking loading sheet.** Onboarding fetches the user's library; the wait can be long, so the surface is a non-dismissable `AdaptiveModalSheet(dismissOnTapOutside = false, dismissOnBackPress = false)` rather than a tiny dialog. The sheet still opens with `EditorialSectionHeader(eyebrow = "Setting up", headline = "Pulling your library together.", description = "Depending on its size, this might take a moment.")`, then a wavy progress indicator below. Container is `surfaceContainerLowest`; back-press and scrim-tap dismissal are disabled, but no close button is added. The result reads like a printed cover-page status line, not a system spinner card.

**A modal sheet is width-adaptive (§2.7).** A bottom sheet welded to the bottom edge of a wide desktop window — a short band under a tall empty scrim, sliding up from below — reads as the phone-derived layout the desktop redesign retires. So a sheet is a **bottom sheet at compact and medium widths** and a **centered editorial panel at expanded width**: a `surfaceContainerLowest` card, ~420dp wide, with a hairline `outlineVariant` border and a large (28dp) editorial corner, height-capped to ~90% of the window (its content scrolls within), and no drag handle. Both forms open with the same canonical header and carry the same body — the form is a chrome decision, not a content one. **Reach for the shared `AdaptiveModalSheet` (foundation `designsystem-core`, `nl.rhaydus.designsystem.component`) for every modal sheet — never a raw `ModalBottomSheet`.** It owns the width branch, the `surfaceContainerLowest` fill, scrim/back dismissal (`dismissOnTapOutside` / `dismissOnBackPress` cover the non-dismissable blocking-loader case), and the panel's drag-handle-replacing top inset; the body it wraps is identical to the one a bottom sheet would host, so a call site never branches on form.

Two ambient hooks let a body react to the form without re-deriving the width class:

- **`LocalModalSheetForm`** (`ModalSheetForm.SHEET` / `PANEL`) — the resolved form, for density and layout. A sheet body steps a phone-sized thumb target down to a desktop pointer target through this — e.g. the progress sheet's primary action drops from a 96dp `ButtonSize.L` on the sheet to a 56dp `ButtonSize.M` on the panel — or reflows for the form: the library filter's facet chips scroll horizontally on the narrow sheet but wrap — and collapse behind a "show more" (`ExpandableFlowRow`, §4) — on the fixed-width panel, which can't scroll a row sideways with a pointer. Read the form, not the window width, so a body stays correct if the sheet→panel breakpoint ever moves.
- **`LocalModalSheetDismiss`** — closes the sheet the way its form should: the bottom sheet animates down first, the panel closes immediately (it has no slide to play). A body calls this from an *in-content* dismiss action (a confirm-and-close button) instead of driving its own sheet state.

### 3.6 Adaptive content width

On a wide window (§2.7) content does **not** stretch edge-to-edge — long-form prose and forms keep a comfortable measure, and list/grid surfaces gain columns rather than wider cells.

- **Reading surfaces** (book-detail body, settings and other forms, profile, any single-column reading column) centre and cap their width at the **reading measure** (~720dp). Apply `Modifier.cappedContentWidth()` (foundation `designsystem-core`, `nl.rhaydus.designsystem.layout`) to the scrolling content column; the page's horizontal gutter still applies inside the cap. Full-bleed media — cover art, hero backdrops, the cover-to-detail morph target — stays outside the cap and spans the surface.
- **List/grid surfaces** cap at the wider **pane measure** (~1100dp) and add columns as width grows (§5 large-window list/grid rule), so a shelf reads as a denser spread, not as a stretched phone column.
- **`TwoPaneScaffold`** (foundation `designsystem-core`, `nl.rhaydus.designsystem.layout`) is the pure-layout primitive backing the expanded-width **list–detail two-pane** pattern (§5): a fixed-width leading pane (the list) beside a flexible trailing pane (the detail), separated by a hairline. It is content-agnostic — the app shell fills it; it owns no navigation. A **null `detail`** collapses it to a single pane (the list fills the full width, no divider); because the list is always the first child either way, toggling `detail` between a value and null keeps the list subtree — and any `movableContentOf` it hosts — in a stable slot instead of tearing it down. The shell uses this so non-pane expanded tabs (desktop Library, Settings) share the same stable list slot as the pane tabs.

## 4. Components

A short catalogue of shared components and what role they play. Anatomy and styling live with the components; this list is so a designer or contributor knows *which* tool to reach for.

- **Top app bar** — page title, optional subtitle, optional back, optional trailing icon actions. Title autosizes within `titleLarge`.
- **Search top app bar** — same skeleton, replaces title with a single-line search field; leading icon flips to a wavy circular indicator while loading. The trailing slot lives *inside* the field: an optional persistent field action (e.g. the barcode-scan glyph on Explore) shows while the field is empty and is replaced by the clear (✕) button once the user has typed — keep search affordances inside the pill, symmetric with the leading glyph, rather than floating a naked icon in the app-bar action area beside it.
- **Editorial search field** — `EditorialSearchField` is the canonical *inline* search input for surfaces that carry their own editorial header rather than a Material search top bar: a fully-rounded `surfaceContainer` pill holding a leading search glyph, a single-line `BasicTextField`, and a trailing clear (✕) button that appears only once there is a query. It lives in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`) and is consumed by the desktop Library and desktop Explore headers. The caller supplies the icons as `RhaydusIconResource` (`searchIcon`, `clearIcon`); the empty-state hint adapts via `placeholder` ("Search this shelf…" on Library, "Search books, authors…" on Explore). Reach for it when a static editorial layout wants a persistent search field beneath its title; use the **Search top app bar** instead when search *is* the app bar (the mobile pattern).
- **Desktop tooltip** — `DesktopTooltip(text) { control }` wraps an icon-only control in a hover tooltip on desktop and is a no-op pass-through on touch (§2.5 desktop tooltip). Reach for it on every icon-only desktop control; controls with a visible text label do not get one.
- **Desktop context menu** — `DesktopContextMenu(items) { surface }` wraps a surface in a right-click menu on desktop (`ContextMenuArea`) and is a no-op pass-through on touch (and when `items` is empty), §2.5 desktop selection. `DesktopContextMenuItem(label, onClick)` is one entry. Reach for it for the desktop secondary-click affordance on an item that touch reaches via long-press.
- **Bottom navigation** — tab destinations for the four roots, the **compact-width** chrome (§2.7). Provided as a docked bar (full-width, attached to the system inset) and a floating toolbar variant; pick docked unless the screen explicitly calls for a hovering bar over scrolling media. It is **app-shell code, not a `core/presentation/component`** — `DockedBottomNavigationBar` / `BottomFloatingBar` live at the orchestration tier (`orchestration/presentation/`) alongside the `TabNavigator` host, because they enumerate the concrete feature tabs. Reusable building blocks they rely on (`RhaydusIconToggleButton`, icon/color roles) stay in `core`.
- **Navigation rail** — the **medium-width** chrome (§2.7): a vertical `NavigationRail` that replaces the bottom bar between 600 and 840dp. Same destinations, selection, app-update badge, and library pulse as the bottom bars.
- **Editorial sidebar** — the **expanded-width** chrome (§2.7): a permanent sidebar (`>= 840dp`) carrying the app wordmark in the editorial `pageTitle` voice over the four destinations, each a selectable row in the app's selected-chip colours (`secondaryContainer` / `onSecondaryContainer` when active, `onSurfaceVariant` idle). Replaces the rail. Like the bottom bars, the rail and sidebar are **app-shell code at the orchestration tier** — they enumerate the concrete feature tabs. All four chromes are driven by one shared `rememberNavItems()` source (`orchestration/presentation/`) so selection, badge, and pulse can never drift between them; the reusable building blocks stay in `core`.
- **Button** — five styles (filled, tonal, elevated, outlined, text) across five sizes (XS → XL). Filled is the page's primary action; tonal is a secondary action that still wants weight; outlined and text are tertiary. One filled action per region — never two competing primaries.
- **Toggle button / icon toggle button** — same size scale as Button; the active state expresses itself via shape morph and fill, not via a separate badge.
- **Split button** — a single primary action paired with an attached chevron that opens a menu of related variants (e.g. "Mark as reading" + alternative shelves). Reach for it when an action has one obvious default and a small set of equivalents.
- **Pill chip** — `PillChip` is the canonical fully-rounded (`RoundedCornerShape(percent = 50)`) chip: a `Surface` carrying a single `labelMedium` label. It backs both the library filter facets and the book-detail tag chips, so the chip anatomy lives in one place — reach for it instead of hand-rolling a `Surface`-and-`Text` pill. Selected → `secondaryContainer` / `onSecondaryContainer` (label semibold); idle → `surfaceContainerHigh` / `onSurface` (label medium). *(This is the authoritative idle colour for the pill-chip anatomy; older prose that says `surfaceContainer` / `onSurfaceVariant` for unselected chips predates the extraction and should be read as `surfaceContainerHigh` / `onSurface`.)* Pass `onClick` for an interactive chip (toggles, filters); omit it for a **read-only** chip — the surface then carries no ripple and no click role, the mode used for the book-detail tag chips. A `concealed` flag renders the chip as a **spoiler redaction** (§2.1 spoiler register): the label is drawn `Color.Transparent` so it still reserves its width but cannot be read, beneath a solid `spoilerCover` fill — the same treatment `ReviewDocumentText` gives an inline spoiler run. Because the hidden label still measures at full width, revealing it (re-render with `concealed = false`) does not reflow the row. Used for book-detail content-warning chips.
- **Expandable flow row** — `ExpandableFlowRow` is the canonical wrapping chip/tag container for a set that can grow unbounded. It wraps items across lines and, past `collapsedLines`, collapses to that many lines behind a trailing **"show more"** affordance; each tap reveals `linesPerExpand` more lines until everything shows and the affordance disappears — a *gradual*, line-based reveal (built on `FlowRow`'s `maxLines` + `FlowRowOverflow.expandIndicator`), so a long set never buries the content beneath it. Both bounds are caller-set; the trailing affordance defaults to an editorial `surfaceContainerHigh` / `primary` pill matching `PillChip`'s anatomy but can be replaced via `showMoreIndicator`. Its `content` is a plain slot (no `FlowRowScope` receiver) so a call site needs no experimental opt-in. The library filter's facet chips use it on the desktop panel form (§3.5) — where a fixed-width panel can't scroll a chip row sideways — while the narrow bottom sheet keeps each facet on one horizontally scrolling line. Reach for it for any wrapping chip set that can run long; do not hand-roll a `FlowRow` with manual slice-and-count state.
- **Edition image** — the canonical book cover. Always 2:3 aspect, subtle radius, optional soft shadow tinted by edition. Falls back through edition → default edition → URL → shimmer placeholder. A final **coverless-title** rung is opt-in via `coverlessTitle`: when no source resolves (or a known URL fails to load) and the data is not still loading, instead of a blank tile the cover is painted as a *coverless cover* — a filled `surfaceContainerHighest` card (imagery cards keep a container shade, §2.1 — never `primary`) carrying the title centred in the editorial Fraunces voice (`headlineMedium`, autosized down to fit the tile). It is opt-in because it only earns its place where no adjacent title text exists: the cover-only library layouts pass it; the detail grid/list layouts, which already show the title beside the cover, leave it null and keep the blank-on-missing behaviour. Never use a raw image loader for covers.
- **Loading dialog** — full-screen blocking wavy progress indicator for unavoidable waits; prefer inline shimmer on cards when the wait is short or the surface can stay interactive.
- **Pull-to-refresh indicator** — the Material 3 Expressive `ContainedLoadingIndicator` inside a `PullToRefreshDefaults.IndicatorBox` is the canonical pull-to-refresh affordance. This is a deliberate exception to the "wavy progress, always" rule (DS §2.5, §6): the wavy circular indicator visually competes with the pull gesture's own arc and reads as off at this size, while the contained loading indicator's morphing shape carries the same expressive character without the conflict. Reach for the wavy primitive everywhere else progress is shown.
- **Pull-to-refresh eyebrow** — `PullToRefreshEyebrow` is the canonical eyebrow for any screen that hosts a pull-to-refresh surface. It lives in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`). It renders the same accent-bar + eyebrow anatomy as a static `SectionLabel`, but swaps the label to a contextual refresh copy ("Refreshing your shelf…", "Catching up on your reading…") while the user pulls and during the subsequent refresh, then flashes the base label briefly in italic on revert. Wired internally: the eyebrow consumes the same `PullToRefreshState` already passed to `PullToRefreshBox`, listens to its `distanceFraction`, and fires a single `threshold` haptic at the trigger crossing (re-armed once the gesture relaxes). Reach for it on every refreshable root surface; do not hand-roll the eyebrow swap or the trigger haptic at call sites.
- **Rhaydus shimmer image** — the canonical loader for non-cover images (avatars, author photos, any free-aspect imagery). Provided by the foundation **`designsystem-image`** module (`nl.rhaydus.designsystem.image.RhaydusShimmerImage`). Use it rather than reaching for a raw image library; it shares the project's Coil loader, shimmer placeholder (suppressed under reduced motion), and `SkeletonCrossfade` behavior. Signature: `(model: Any?, contentDescription: String?, modifier, contentScale, isLoading)`. `EditionImage` is for book covers only — everything else uses `RhaydusShimmerImage`.
- **Update progress sheet** — modal sheet for editing reading progress. Hosts the canonical `pages | percentage | time` segmented switcher with a hero numeric input, an editorial suffix line, and a wavy progress bar. The switcher is **format- and total-aware**: the primary unit is `time` for an audiobook (`BookEdition.isAudiobook`, which is keyed off the edition's `ReadingFormat`, not whether a duration happens to be present) and `pages` otherwise, and `percentage` is offered **only when the matching total is known** (page count for print, duration for audio) — without it a fraction can only ever resolve to 0, so the tab is hidden rather than shown broken. When that total is unknown the sheet drops to the primary unit alone, hides the "of N …" suffix and the progress bar, and accepts free numeric/time entry (no clamp-to-total). New "edit a single number on a book" surfaces should look at this sheet before inventing a new one.
- **Editable hero-stat field** — `HeroStatNumberField` is the shared "edit a single number framed as a hero" control (with its `EditorialSuffix` caption): a borderless `BasicTextField` rendered in the editorial `statLarge` face, cursor tinted `primary`, width sized to the character count so it reads as a hero numeral rather than a boxed form field. Both live in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`). It is the canonical input behind both the Update progress sheet and Focus Mode's page entry. Reach for it for any number the user edits in a hero context; **never** use a bordered `OutlinedTextField`/`TextField` for that role — the box clashes with the editorial register.
- **Deadline badge / cover overlay / summary line** — the family of components that mark a book as time-bound. Used together when a book's deadline matters; never mixed with a stale rating row in the same card.
- **Unreleased badge** — `UnreleasedBadge` is the canonical mark for a book whose effective release date is in the future. Two styles: `Compact` ("Out MMM d", with year appended only when not the current year) sits as a top-start overlay on cover art in carousels and grid cards; `Prominent` ("Releases MMMM d, yyyy") sits inline beneath the hero byline on book detail. Surface is `primary` / `onPrimary` so the chip reads as a deliberate publishing signal rather than another deadline state. When the prominent variant is shown on book detail, suppress the trailing release year in the byline so the date isn't named twice. The "is it unreleased?" check is centralised on `Book.isUnreleased` — never compare dates at the call site.
- **Haptics helper** — the single entry point for haptic feedback. Exposes eight semantic cases. No ad-hoc haptics — never call `performHapticFeedback` from a call site; always go through the helper. The "no mixed icon families" rule (§2.6) has a sibling here.
  - **commit** — a user-triggered action succeeded (mark-as-read, save, confirm). Celebratory in texture; reserved for commit-class actions, never navigation taps.
  - **reject** — an optimistic mutation rolled back, or an action refused. Pair with the shake-on-error visual (§2.5).
  - **select** — a soft tick on neutral selection: shelf chip toggle to a non-read state, segmented switch in a sheet, tab change in a carousel filter. Distinct from *commit* (which celebrates) and *reject* (which rolls back).
  - **threshold** — a single firm tap when the user crosses a meaningful boundary: pull-to-refresh trigger point, drag-to-reorder pickup, long-press peek activation. No celebratory texture.
  - **tickle** — a per-integer tick during a slider or picker drag. Each integer crossing on the rating control or progress page-number input fires one tick.
  - **lift** — drag-to-reorder pickup. Says the item has left the page; pair with the visual lift.
  - **drop** — drag-to-reorder settle. Distinguishable from *lift* so the item's return to the page is felt.
  - **milestone** — a two-pulse haptic above *commit* for natural progress events: completing a year-end reading goal, hitting a 30-day streak, finishing the last book in a series. Reserved for moments that are bigger than a save.
- **Mark-as-read celebration** — `MarkAsReadBurst` is the canonical hero moment for a successful mark-as-read commit. It paints a radial particle burst (primary + tertiary tinted) outward from the centre of its footprint; replays whenever `triggerKey` changes; suppressed under reduced-motion (§2.5). Compose it as a sibling overlay (`Modifier.matchParentSize()` or `Modifier.fillMaxSize()`) on whichever surface owns the commit — the shelf-action card on book detail and the reading screen at full-screen scale. Always pair the trigger with a single *commit* haptic so the visual and haptic land together. Do not reach for it on other status transitions — read is the only shelf change that earns a celebration.
- **Animated stat number** — `AnimatedStatNumber` is the canonical way to render a numeric stat that can change in place (profile stats, pages-read counters, deadline pacing). Tweens between values via `animateFloatAsState`, forces tabular figures so digits don't jitter mid-tween, and snaps when the user has disabled system animations (§2.5). Each integer crossing during the tween fires a brief 1dp hairline pulse below the number, tinted with the same content colour as the number itself so the tick reads against any surface (including the primary-filled hero card, where the number is `onPrimary`) — a quiet ledger tick that makes a count feel earned rather than rolled; suppressed under reduced motion. Reach for it whenever a number on screen is bound to live state — pair it with the wavy progress indicator under the Hero stat pattern (§5) so bar and number move as one motion. Raw `Text` for a number that can change should be treated as a bug.
- **Lazy-item mutation animator** — the canonical wiring for animating add / move / remove on a lazy list when the change is user-triggered. `rememberLazyItemMutationAnimator(keys)` snapshots the initial set of keys on first non-empty composition; the `Modifier.mutationAnimated(scope, animator, itemKey)` extension (overloaded for `LazyItemScope` / `LazyGridItemScope`) returns a `Modifier` (carrying `Modifier.animateItem()` plus a `drawWithContent` accent-bar pulse) that the caller applies to the outermost composable of each lazy item. Apply directly — never via an intermediate `Box`, since an extra layout node interferes with lazy-item measurement. Items added or removed after the snapshot fade and reflow; new items also get a brief 20×1 dp accent-bar pulse (§2.3 inline-bar hairline) at their top edge. Suppressed when system animations are disabled. Use it for shelves and chip rows where the user's own action is the "what changed" signal; do not apply it to carousels backed purely by server data (trending, continue-series).
- **Share card** — `ShareCard` is the single composable that renders any user-facing share artefact (book, hero stat, pulled quote, year-recap slide) into a fixed-aspect editorial composition with a `SOFTCOVER` folio sign-off. Variants are picked by `ShareContent` subtype: book (cover + title + byline + optional rating + optional quote), reading-update (a *personalised* card attributing the book to the reader — see below), stat (`primary`-filled hero with eyebrow + oversize numeral + caption), quote (oversize low-alpha `quoteGlyph` behind italic headline + primary byline), year-recap (eyebrow + display + bulleted highlights). Dimensions live in `ShareCardDimensions`; never override them at the call site. The **reading-update** variant (`ReadingUpdateShareContent`) is the centred-stacked personal card: status eyebrow → cover → title → byline → reader identity (circular `RhaydusShimmerImage` avatar + username) → the reader's own tags (when any) → state-specific tail. The reader's tags render as a centred wrapping `FlowRow` of read-only `PillChip`s beneath the identity; **spoiler-flagged user tags are excluded** from the card (a share image is public, so a tag the reader hid from other readers must not leak) — the call-site mapper drops them before handing the names to `ShareCard`. It carries two states, keyed off the user's shelf status, and deliberately omits any recency wording (the user may share long after the fact): **finished** (`Read`) uses the eyebrow "FROM MY SHELF" and shows the reader's rating as read-only `StarRatingInput` gold stars plus their review, rendered through the shared `ReviewDocumentText` so inline spoiler spans are masked as redaction blocks exactly as on the book-detail review (the whole-review render is *not* gated — only the explicitly-marked spans are concealed); **reading** (`Reading`) uses "CURRENTLY READING" and shows a progress label (`page X / Y · NN%`, text only — no bar). The card-content mapping lives at the call site (the review travels as a structured `ReviewDocument`; the rating is the stored 0–5 value handed over untouched; the progress label mirrors the book-detail block — time (`listened / total`) for audiobooks, pages for print — with the percentage derived from the matching unit counts when known and falling back to `UserBookRead.progress`, which is already a 0–100 value); `ShareCard` only renders. It is offered alongside the editorial book card via a `SingleChoiceSegmentedButtonRow` toggle ("My update" / "Book") inside the share sheet, shown only when the book is on the reader's Read or Reading shelf — off-shelf books fall back to the book card with no toggle. Pair with `CapturableShareCard` + `rememberShareCardCapture` to render the card. The `ShareCardCapture` seam (a `commonMain` interface with Android, iOS, and desktop actuals) owns three actions: `capture.saveToGallery(displayName)` writes a PNG into the device gallery (`Pictures/Softcover/` via MediaStore on API 29+, legacy public-Pictures dir + scan on API 26–28; the iOS gallery save is not yet wired); `capture.saveToCache(displayName)` writes a PNG into app cache and returns its identifier; and `capture.share(displayName)` presents the **platform share sheet** for the card image — the OS-level share is part of the capture contract, *not* the calling surface's job (Android builds an `ACTION_SEND` chooser from a `FileProvider content://` URI, iOS presents a `UIActivityViewController`; desktop has no system share sheet, so it copies the PNG to the system clipboard, and its `saveToGallery` opens a native file-save dialog). A surface that just wants to share the card calls `capture.share(...)` and branches on the returned `ShareOutcome` (`Shared` / `Failure`); it never constructs an intent itself. Legacy storage permission (`WRITE_EXTERNAL_STORAGE`, `maxSdkVersion=28`) is requested through `rememberGalleryWritePermissionRequester` — on API 29+ the requester is a synchronous pass-through. Reach for this rather than building a new share image inline; one renderer, one editorial register, one save path.
- **Staggered entry coordinator** — the canonical welcome-moment animator for carousels and lazy lists. `rememberStaggeredEntryCoordinator()` captures the screen-entry timestamp; `Modifier.staggeredEntry(coordinator, index)` plays a ~240ms upward translate (~8dp) + fade in, delayed by ~60ms per index, but only for items composed within the coordinator's window (default 350ms). Items composed later render statically — never apply this expecting items to animate on scroll. Pair with the mutation animator on the same item modifier when both apply (`mutationModifier.staggeredEntry(...)`). Suppressed when system animations are disabled.
- **Drop-cap text** — `DropCapText` renders editorial body prose with a 3-line drop-cap on the first letter, tinted `primary` by default. It lives in the **foundation `designsystem-editorial`** (`nl.rhaydus.designsystem.editorial.component`). The drop-cap font size is `bodyStyle.lineHeight * 3 * 0.92`; the first three lines of body text indent past the cap, and lines four onward resume at full width. Skips leading whitespace and punctuation when picking the letter; falls back to a plain `Text` for empty or letter-less bodies. Pass `dropCapFontFamily = displayFontFamily()` to render the cap in Fraunces (the Softcover editorial display face) — the parameter defaults to `null` (same family as the body) so the app must supply the font explicitly. Reach for it on book-detail descriptions; do not apply it to inline metadata or to bodies inside cards where the cap would dominate the tile.
- **Swipe row actions** — `SwipeRowActions` wraps a list-layout row in a Material 3 `SwipeToDismissBox` and reveals a coloured background as the user drags. Swipe-right (start → end) is the *mark-as-read* action — tertiary container with `ic_bookmark_check` and "Mark as read" copy; suppressed via `allowMarkAsRead = false` when the book is already in Read. Swipe-left (end → start) is the *remove* action — error container with `ic_delete` and "Remove" copy. Background opacity tracks the swipe progress (`progress * 1.2f`, capped at 1) so the affordance reveals as the user pulls. The dismiss state is reset immediately on commit so the row snaps back; the calling surface is responsible for the data write and for shaking the row on failure (pair with `Modifier.shakeOnError` on the wrapper). Reach for it on the `LIST_COMPACT` and `LIST_LARGE` library layouts; never apply it to grid cards.
- **Star rating input** — `StarRatingInput` is the canonical interactive personal-rating control: a row of five `ic_star_filled` glyphs the user rates against in half-star steps. Empty stars are `onSurfaceVariant` at low alpha; the filled portion is the shared `RatingGold` brand colour (the same gold the read-only community/review rating glyphs use — never re-declare the hex at a call site). Partial fills are drawn by clipping the gold glyph to a fraction of its width, so a `4.5` reads as four-and-a-half stars. Tapping a star commits that value (left half → `.5`, right half → whole); dragging horizontally scrubs and fires one `tickle` haptic (§2.5) per half-step crossing. The committed value is reported through `onRatingChange` once per gesture — on tap or on drag release, never mid-drag — so the caller's write path runs once. A live drag preview overrides the source value visually until the committed value lands back in state. Reach for it wherever a user sets their own rating; pair it with a `SectionLabel` eyebrow. On book detail it is gated to books on the **Read** shelf — a rating can only be added or changed once the book is marked as read — and it round-trips to the existing `user_book` row.
- **Review editor sheet** — `ReviewEditorBottomSheet` is the canonical surface for editing the user's personal review. It follows the modal-sheet rule (§3.5) — editorial header first — then the **review formatting toolbar** (below) and a rich-text `BasicTextField` styled with the editorial body face set **upright** (`editorialTypography.body.copy(fontStyle = Normal)`), wrapped in a 12dp rounded outlined container so it still reads as a field. The base face is deliberately upright, not italic: italic is now a *semantic mark* the user applies, so default text must be distinguishable from emphasised text. The user selects text and toggles bold / italic / spoiler; the field styles the marks live via a `VisualTransformation` (bold weight, italic slant, and the translucent `spoilerEditorHighlight` wash behind a spoiler run, which stays legible so the author can read what they wrote). A "Contains spoilers" `Switch` row — the *whole-review* gate, distinct from inline spoiler marks — sits below the input. Actions are stacked, full-width: **Save** (filled — publishes the structured review, disabled while the body is blank) and **Delete review** (text — shown only once a review exists). The sheet owns its **editing buffer** (text + marks + the spoiler-switch state) as transient local state seeded once from the incoming `ReviewDocument`, and reports the finished document only on save. There is **no draft persistence** — a save round-trips to the server (offline-replayable) and the on-screen copy is overwritten by the server's canonical `review_slate` on the next refresh. On book detail it is reached from the **Review section** and, like the rating control, is gated to the **Read** shelf. Reach for it for personal long-form text the user publishes; do not reuse it for private marginalia (notes).
- **Review formatting toolbar** — `ReviewFormattingToolbar` is the inline bold / italic / spoiler control row for the review editor. It uses the app's pill-chip anatomy (§3.4 / inline filter chip strip): three fully-rounded **word toggles** — `Bold` (rendered bold), `Italic` (rendered italic), `Spoiler` — so the row reads as one deliberate control rather than loose buttons, and the bold/italic chips preview their own effect. Active → `secondaryContainer` / `onSecondaryContainer` (the app's standard selected-chip colours); idle → `surfaceContainer` / `onSurfaceVariant`. Each chip reflects whether the *whole current selection* already carries that mark; with no selection to act on the entire row dims (≈0.45 alpha) and is inert. Reach for it only inside the review editor; it is not a generic rich-text bar.
- **Review document text** — `ReviewDocumentText` is the canonical renderer for a stored review (`ReviewDocument`) wherever one is displayed read-only — the personal review card and community review cards both use it. The base face is **upright** (italic is a per-run mark, not the default voice); bold and italic runs are styled inline; a run marked as a spoiler is hidden under a solid `spoilerCover` block (text drawn transparent over the block) until the reader **taps that span** to reveal it, tracked as transient per-span state. This inline reveal is independent of any whole-review "Show spoiler" gate the caller wraps around it. A tap that does *not* land on a concealed spoiler invokes the optional `onClick` (so the surrounding card still opens on tap). It exposes `maxLines` / `overflow` / `onTextLayout` so callers can drive their own "Show more" affordance. Reach for it for any displayed review body; never render review content through `htmlToAnnotatedString` (that path is for server HTML like book descriptions, not reviews).
- **Session peek bar** — `SessionPeekBar` is the persistent live-timer bar that rides above the bottom navigation whenever a reading session is active. Anatomy: a `surfaceContainerHigh` rounded bar holding a 32dp `EditionImage` cover thumbnail, the book title (`titleSmall`, single line), a live `H:MM:SS` timer beneath it (or `Paused · …` when paused), then inline pause/resume and stop `IconButton`s. The whole bar is tappable and opens Focus Mode. It reads the app-scoped `ActiveSessionController` (never its own session state) and renders nothing when no session is active, sliding in/out with `slideInVertically + fadeIn` / `slideOutVertically + fadeOut`. Pause/resume fires a `select` haptic, stop fires `threshold` (§2.5). It is mounted once, above the nav in both the docked and floating bar styles — never duplicated per screen. Reach for it only as the global session surface; do not build a second timer bar. On the **wide shell** (medium/expanded, where there is no bottom bar for a floating pill to ride over) it renders its **flush** form (`flush = true`): an edge-to-edge strip with square corners and a leading top hairline, docked at the foot of the content pane — the desktop now-playing convention — rather than the rounded floating card the compact bottom bar carries.
- **Barcode scanner** — `BarcodeScanner` is the canonical full-bleed camera surface for reading a book's barcode. It hosts a CameraX `PreviewView` (back camera) and feeds frames to the **bundled** ML Kit barcode model (no Google Play Services dependency), constrained to `FORMAT_EAN_13` / `FORMAT_EAN_8` — the formats printed on physical books, so unrelated codes never register. Editorial chrome rides over the live feed: a top scrim carrying a `SCANNING` eyebrow + `headlineMedium` instruction in white (the one place light-on-media copy is allowed, since the surface is a camera feed, not a theme surface), and a centred rounded viewfinder reticle. It emits the **raw value of the first barcode it reads exactly once** via `onIsbnDetected(raw)` and then stops analysing; it is deliberately **stateless about resolution** — turning the raw string into a book, and deciding what an unknown book means, belongs to the call site (see `feature/scan`), never to this leaf (the same "handoff leaves through the call site, never the leaf" rule the External-links strip follows, §5). Camera permission is gated separately via `rememberCameraPermissionRequester` (modelled on the notification/gallery requesters); when permission is denied or the device has no camera, the calling screen falls back to manual ISBN entry rather than rendering this component. Reach for it for any in-app barcode capture; do not hand-roll a second CameraX/ML Kit pipeline.
- **Tag editor sheet** — `TagEditorBottomSheet` is the canonical surface for managing the user's *own* tags on a book (§3.5 modal sheet — editorial header first). Anatomy: the current tags listed at the top, each as a row of `[name PillChip] … [Spoiler toggle PillChip] [ic_close remove IconButton]` (the Spoiler chip is a selected/idle `PillChip` toggle, distinct from the review editor's whole-review spoiler switch — here it is **per tag**); then an "Add a tag" block — a `FlowRow` of the four Hardcover categories (**Genre / Mood / Tag / Content warning**) as selectable `PillChip`s, a single-line rounded `OutlinedTextField` for the tag name (trailing `ic_close` clear, IME **Done** commits), and a full-width tonal **`Add tag`** button that commits the typed name into the selected category. There is **no search/autocomplete** — the `_ilike` tag search is disallowed by the API (compute cost), so the user simply names the tag and the upsert reuses an existing tag of that name or mints a new one server-side. A full-width filled **`Done`** button at the foot dismisses the sheet. The sheet is a dumb renderer — every add / remove / spoiler-toggle is reported through a callback and committed by the caller via the **complete-set upsert** (see "Your tags section"). Reach for it for self-tagging any entity; do not reuse it for the editorial (read-only) tag block.
- **Choose-lists sheet** — `ChooseListsBottomSheet` is the canonical shared surface for adding/removing one or more books to the user's custom lists (§3.5 modal sheet — editorial header first). It is a **shared `core/presentation/component`** consumed by both `book_detail` (single book) and the library **bulk-select** pattern (§5, a `Set<bookId>`), so it generalises over a set of book ids. Anatomy: an `EditorialSectionHeader`, then a `LazyColumn` of the user's custom lists each rendered as a row carrying a **tristate** membership glyph — `ListMembership.NONE` / `PARTIAL` / `ALL` — where `PARTIAL` means some-but-not-all of the selected books are in that list; tapping commits toward the larger end (`PARTIAL` → `ALL`, `ALL` → `NONE`), matching the standard tristate-checkbox UX. A row mid-mutation is disabled (its id is in `listsBeingMutated`) and shows a `CircularProgressIndicator`, so optimistic writes read cleanly. A trailing "Create new list" row delegates to the caller's `onCreateNewListClick` (which opens `CreateListScreen`). The sheet is a **dumb renderer** — every toggle and the create action are reported through callbacks; the caller owns the `AddBookToListUseCase` / `RemoveBookFromListUseCase` writes and decides whether to stay open for consecutive adds. Membership is computed from the supplied `customLists` via the `BookList.membershipFor(bookIds)` helper that ships with the component. Reach for it for any add-to-list affordance; do not build a per-screen list picker.
- **Connectivity chrome** — `ConnectivityBanner` (a transient "you're offline" banner shown by the app shell) and the `OfflineGuard` helpers `rememberIsOnline()` + `OfflineScreenContent` (a full-surface empty-state for a screen whose content cannot load offline) are **shared `core/presentation/component`s**, consumed by the shell (`RootScreen`) and any feature screen that must degrade offline (e.g. `explore`, `book_detail`). They read network availability through the `core:domain/connectivity` contracts — no feature owns them. Reach for `OfflineScreenContent` for any "needs the network" empty state; do not hand-roll a per-screen offline placeholder.
- **Active reading session** — `ActiveSessionController` is the **app-scoped single source of truth** for the running reading session (`core/presentation/session`), exposed as a `StateFlow` and consumed by the peek bar, Focus Mode, the reading tab, and the lock-screen foreground service. It is a shared `core` controller (not a feature internal) because ≥2 surfaces drive it. It launches the platform foreground service through the `ReadingSessionLauncher` **contract** (impl in `feature/session`), so core never depends on the service. `SessionPeekBar` and `FocusModeScreen` are the feature-owned surfaces that render its state.
- **Personal review section** — the book-detail entry point into the review editor. Renders a `SectionLabel("Your review")` over a single tappable `surfaceContainerHigh` card: an editorial **"Write a few words…"** prompt when no review exists, otherwise the review rendered via `ReviewDocumentText` (upright editorial body), clipped to `REVIEW_COLLAPSED_LINES`, with a quiet "contains spoilers" footnote when the whole-review flag is set. Tapping anywhere on the card — including the rendered text, except a concealed spoiler span — opens the review editor sheet seeded with the current structured review. It sits directly beneath the star-rating row on the Read shelf so a reader's rating and words live together. The review rides on the cached `user_book` row (as a structured `review_slate`), so it arrives with the book and reflects edits made elsewhere — no separate load, no skeleton, no flash.

## 5. Patterns

Recurring recipes that compose the primitives above.

- **Editorial section.** Accent bar (optional) → eyebrow → display headline → body (carousel, list, or block). The default way to introduce any region.
- **List–detail two-pane.** On expanded windows (§2.7) a root list surface (library, reading, explore) keeps its list/grid in a fixed-width leading pane and renders the selected book's detail in the trailing pane, backed by `TwoPaneScaffold` (§3.6). Selecting a book swaps the trailing pane **instantly** — the cover-to-detail morph (§2.5) is a property of the compact full-screen push, not the pane swap, so the pane host suppresses it. Before a book is chosen the trailing pane shows a quiet editorial placeholder, never a blank surface. The pattern is **expanded-only**: at compact and medium widths the same tap pushes the detail full-screen as before — the shell's `BookDetailPresenter` (not the feature) owns the push-vs-pane decision, so a list screen stays unaware of which it gets. Tabs that don't open book detail (Settings) stay single-surface in the *shell* sense (they never take the book-detail trailing pane), and full-screen pushed surfaces (focus mode, scanner, full-screen cover) plus onboarding are exempt — they render outside the shell and stay full-bleed.

- **Desktop settings master–detail.** A menu-style tab whose sub-screens are settings forms (not book detail) gets its own *feature-internal* master–detail on desktop (`jvmMain`), analogous to Library's shelf-sidebar (§the list/grid rules): a category **source-list** sidebar (`hoverHighlight` + `pointerHandCursor` rows, `secondaryContainer` on the selected row) beside a detail pane that swaps **inline** — selecting a category never pushes. Settings is the reference: *Account → Your profile* still pushes full-screen (Profile is its own surface), while *Appearance* and *Library tabs* swap the pane, each scrolling under a `DesktopVerticalScrollbar`, with the Library-tabs save bar docked at the pane's bottom. The sub-screen bodies are shared composables (mobile wraps them in a pushed `SoftcoverTopBar` page; desktop hosts them in the pane and in a standalone back-bar fallback). The hosted sub-screen's model is acquired in the tab's `Content` (Voyager's `koinScreenModel` is a `Screen` extension and resolves only in `commonMain`), gated by a per-feature `expect val` so mobile doesn't create it — mirroring `wideGridTabsUseDetailPane`. **Desktop Library and Explore opt out of the two-pane** (each has a bespoke full-width layout — Library's shelf-sidebar + adaptive grid, Explore's discovery grids — where a side detail pane only starves the grid): on the desktop (`jvmMain`) target neither wide-grid tab is detail-capable, so a tapped book pushes the detail full-screen — while mobile/tablet keep their two-pane. Reading, a detail-style reading list, keeps the two-pane on every platform. The opt-out is the platform seam `wideGridTabsUseDetailPane` (Library and Explore are both gated on it); `BookDetailPresenter` fills the pane only when the current tab is detail-capable on an expanded window, and pushes otherwise.
- **Hero stat.** A single oversize number in `statHero` or `statLarge`, an editorial suffix beneath in italic body, on-surface-variant. Used for "books read this year", "pages today", and progress sheets. The unit (e.g. "pages", "books") is named in the eyebrow above the number, never trailed next to it — pairing a unit suffix with the oversize numeral fights for horizontal space and breaks once the number grows. The number itself uses single-line autosize down from `statHero` so power-reader counts (six- or seven-digit page totals) still fit the card without reflowing the layout. The numeral is rendered via `AnimatedStatNumber` (§4) so changes tween in place — raw `Text` for a live-bound stat is a bug.
- **Editable hero stat.** Same as hero stat, but the number is editable — rendered through the shared `HeroStatNumberField` component (§4): a borderless `BasicTextField` styled with `statLarge`, cursor in primary colour, width computed from character count so the field does not jump as digits are typed. Pair it with an `EditorialSuffix` caption ("of 195 pages", "of the way through"). Used by the Update progress sheet and Focus Mode; do not hand-roll a boxed field for an editable hero number.
- **Editorial quote.** Oversized low-alpha `quoteGlyph` (tinted `onSurfaceVariant`) behind an italic headline-medium pull quote, with a primary-coloured byline beneath. Used to surface notes, reviews, or a featured passage. The same glyph treatment also serves as a decorative flourish in empty states (e.g. "no books currently reading"), where the quote text below is replaced by an italic encouragement headline and no byline. In empty states only, the glyph plays a slow infinite ±2° sway (~6.8s each direction, FastOutSlowIn) via `Modifier.quoteGlyphSway()` — a magazine pull-quote breathing, never a marquee. Do not apply the sway to populated quote cards (review cards, share cards) — content next to the glyph fights a moving mark for attention. Suppressed under reduced motion (§2.5 gate).
- **Spoiler reveal.** A review hides its spoilers at two independent granularities. The **whole-review gate** is for a review flagged as containing spoilers: the body is withheld behind a quiet "Show spoiler" text button (reveal state held transiently per review id) — used on community review cards. The **inline span reveal** is for individual spoiler runs *inside* an otherwise-visible review: the run is rendered as a solid `spoilerCover` block (text drawn transparent) and reveals in place when the reader taps that span (see `ReviewDocumentText`, §4). The two compose — a review can be gated as a whole *and* contain inline spoiler spans — but they are separate affordances; never collapse one into the other. In the editor, the same inline mark previews as the translucent `spoilerEditorHighlight` wash so the author keeps reading their words.
- **Reserved-row card.** Carousel and grid cards reserve vertical space for every optional row they may show, so the row of cards never reflows as data streams in.
- **Tonal grouping.** When two regions need to feel distinct on the same page, step the container shade rather than drawing a divider or adding a card outline.
- **Inline filter chip strip.** A horizontally scrolling `Row` of pill-shaped chips placed directly above a grid or list to scope its contents (e.g. the Library "Read" tab's year chip row). Selected chip swaps to `secondaryContainer` / `onSecondaryContainer`; unselected sits on `surfaceContainer` / `onSurfaceVariant`. Always include a leading "All …" chip that clears the filter. Reuse the same chip anatomy as the shelf tab pills (§3.4); do not apply the carousel page-edge serif hint (§3.4) — the chip strip is a filter affordance, not a peek-affordance. On an **expanded** (desktop / large) window the strip **wraps** (`FlowRow`) rather than scrolling horizontally, since a pointer can't fling a chip row sideways on a fixed-width pane; compact/medium keep the horizontal scroll.
- **Active-filter chip row.** Distinct from the inline filter chip strip above: this row renders only the *currently applied* filters as removable input chips, with the picker living in a separate modal sheet. Each chip is `secondaryContainer` / `onSecondaryContainer`, the label sits on the start, and a trailing `ic_close` glyph (14dp) marks it removable on tap. Chips enter and leave via `expandHorizontally` + `fadeIn` / `shrinkHorizontally` + `fadeOut` so the mutation reads as part of the surface's editorial register, not as a pop-in. When more than one chip is active, append a tonal "Clear all" chip on `surfaceContainer` / `onSurfaceVariant` as the row's final element. On an **expanded** (desktop / large) window the row **wraps** (`FlowRow`) instead of scrolling horizontally — a fixed-width pane can't fling a chip row sideways with a pointer — while compact/medium keep the horizontal scroll; this mirrors the filter sheet's panel-form wrap (§3.5). Reach for this row whenever the picker UI is decoupled from the active set — multi-facet library filters, future faceted searches, anywhere the question "what's narrowing my view right now?" needs to be one-tap reversible. The picker itself follows §3.5's modal sheet anatomy with one `FacetSection` per facet (Title label + horizontal pill row), populated only from facet values actually present in the surface's source content so chips never narrow to empty.
- **Book-detail tag block.** The read-only display of a book's tags on book detail, grouped into the three Hardcover tag categories — in order **Genre**, **Mood**, **Content warning** — each showing the top 5 tags by popularity (`taggable_counts.count`). It sits after the About section. A `SectionLabel("Tags")` heads the block; each category gets a `labelLarge` semibold `onSurfaceVariant` sub-label over a **wrapping `FlowRow`** (8dp horizontal + vertical spacing) of read-only `PillChip`s — *not* the horizontally-scrolling `Row` the library facet sections use. The wrap is deliberate: the set is capped at 5 per category and lives in a full-width scrolling column, so all chips should be visible at once rather than hidden behind a scroll affordance. (This is the app's first `FlowRow` usage; reach for the same wrapping block for any capped, full-width set of label chips.) Empty categories are omitted, and the whole block is skipped when a book has no tags so no empty section renders. **Content-warning chips are concealed by default:** each renders at its true size but under a solid `spoilerCover` block (clipped to the pill shape), revealed in place — one chip per tap — exactly like the inline review spoiler reveal (§5 / `ReviewDocumentText`), since a content warning can itself be a spoiler. Each chip's reveal is held in `rememberSaveable` keyed by tag id, so an unveiled chip stays unveiled when the section scrolls out of the `LazyColumn` and back (a plain `remember` would re-veil on every recycle). Genre and Mood chips are shown plainly.
- **Your tags section.** The book-detail display of the user's *own* tags — distinct from the read-only, popularity-ranked editorial **Book-detail tag block** above. It sits **directly below the shelf-action bar and above the rating/review**, and renders **only when the book is on a shelf** (`book.userBook != null`) — tagging is offered for shelved books only. A `SectionLabel("Your tags")` heads it; the tags render as a **single flat wrapping `FlowRow`** of read-only `PillChip`s (8dp spacing) — *not* grouped per category like the editorial block, since a reader's set is small and personal. The user's own tags show **plainly** (spoiler-flagged ones included — this is the reader's private view; the spoiler flag only hides them from *other* readers on the share card). The row ends with a selected-styled **`Edit tags`** chip that opens the **Tag editor sheet** (§4); when the user has no tags yet the section shows a single **`Add tags`** chip instead. Edits are **optimistic**: the new full set lands in state at once, then the whole set is re-sent through the `upsert_tags` mutation (the backend replaces the complete set, so a removal is "save without it" and a spoiler toggle is "save with the flag flipped"), and the canonical server response overwrites state on success or rolls back on failure (the global error toast already fires). Reach for this pattern for any user-owned tagging surface; keep it separate from the editorial tag block.
- **View-control strip.** A horizontal row that pulls a list/grid surface's view-shaping controls — sort, filter, layout — out of the top app bar and lands them directly above the content they shape. Anatomy: leading-aligned pills (`Surface` with fully-rounded shape, leading 16dp icon, `labelMedium` semibold label, optional trailing chevron or status dot), a `Modifier.weight(1f)` `Spacer`, and a trailing icon-button for any view-density toggle (e.g. grid/list layout). Pills sit on `surfaceContainer` / `onSurfaceVariant` by default and swap to `secondaryContainer` / `onSecondaryContainer` only when the control is in a *non-default* state ("filters are applied" — not "a sort is set", because a sort is always set). Each pill carries its current state inline as part of its label (`Sort: Date added ▾`), so the user can read state without opening the menu — the chevron at the tail is the affordance to change it. The **trailing cluster** holds icon-buttons (no label) for actions that don't carry independently-readable state and shouldn't compete with the leading pills for width — the layout/density toggle today, and a conditional **mode toggle**: the Library strip grows a drag-handle icon-button there only when the current tab is on a positional sort with reorderable content, which toggles into and out of Rearrange mode (plain chrome idle, `secondaryContainer` filled while engaged — see "Rearrange mode" in §5). A labelled pill was tried for this and dropped: a third leading pill doesn't fit alongside Sort + Filter + Layout on a narrow phone and truncates — mode toggles belong in the trailing icon cluster, not as a fourth pill. The strip uses 24dp horizontal page gutter and 8dp spacing between pills, sits below the tab row (and below any per-tab chip rows like the Read-year strip), but *above* the active-filter chip readout — picker affordance first, then the readout of what's currently applied, then the content itself. Hides during bulk-select mode (selection has its own bar) and animates with the same `expandVertically` + `fadeIn` / `shrinkVertically` + `fadeOut` register the chip rows already use. Reach for this pattern on any root list/grid surface whose top bar would otherwise stack three or four mute icon buttons (Library is the worked example); do not introduce it on a surface that already passes the icon-count sniff test or where the controls don't carry independently-readable state.
- **Inline pacing nudge.** A dismissable one-liner in italic body copy tinted `primary`, placed in-flow above the card it speaks to. Used on the Reading screen to surface a per-day pacing target derived from an active deadline. Carries a trailing icon-button close affordance (no copy beyond the message itself). Persistence is per-book-per-day; once dismissed, the row stays gone until the local date rolls over. Reach for it when a single sentence of guidance derives from existing state and should not earn the weight of a card or sheet.
- **Actionable inline banner.** The nudge's heavier sibling: when an in-flow prompt needs a *primary action* (not just acknowledgement), promote it to a `surfaceContainerHigh` rounded card (24dp page gutter, 16dp radius) holding an eyebrow (`eyebrowSmall`, `primary`), one italic `bodySmall` sentence, and a single tonal `RhaydusButton` (`ButtonSize.S`) — with a trailing `ic_close` `IconButton` to dismiss. Used on book detail when arriving from a barcode scan and the book is already on a shelf with a *different* edition ("Already on your shelves — update it to the one you scanned?"); the button routes to the edition-update action, dismiss hides the offer while the scanned edition stays displayed. It sits **directly beneath the shelf-action section** it speaks to, not above it. While the action is in flight, the tonal button is **replaced** by a 20dp `CircularWavyProgressIndicator` + an "Updating edition…" `bodySmall`/`onSurfaceVariant` line — this both signals progress and removes the tap target so the action can't be fired twice (the action also self-guards on its in-progress flag). One tonal action per banner (never two competing buttons); the banner is rendered as its own list item and omitted entirely (not space-reserved) when its condition is false. Reach for it when a transient, condition-gated prompt carries a concrete next step; reach for the lighter pacing nudge when no action is offered.
- **Standfirst.** A book's `headline` — a one- or two-line editorial introduction owned by the book itself (not the edition) — rendered as a magazine *standfirst* (the bold lead between a title and its body). It opens the book-detail **about section**: directly under the `About` `SectionLabel`, set in the editorial `bodyLarge` role (italic Fraunces, `onSurface`) so it reads as a subtitle/lead rather than a competing headline, with a gap (≈16dp) before the drop-cap description body begins. It sits in the editorial italic voice deliberately — a roman title/`titleMedium` register would read as structural chrome, and a `headline`-scale role oversizes a one-sentence intro into three wrapped lines. The title lives in the cover hero above, so the standfirst is the page's first on-`surface` editorial voice and leads the eye straight into the description — title → standfirst → body, the classic spread rhythm. It is plain text, never run through `htmlToAnnotatedString` (that path is for the server-HTML description below it). Suppressed when the book has no headline; when a headline exists but the description is empty, the standfirst stands alone and the "No description…" fallback is omitted. Reach for it wherever a record carries a short curated lead distinct from its long body; do not promote it to its own section header or reuse the section-headline `display` role (that would compete with the section eyebrow).
- **Edition colophon line.** A single-line `bodySmall` / `onSurfaceVariant` strip that surfaces print-edition specifics — publisher, ISBN-13, and ISBN-10 today, scoped to the user's currently-selected edition — sat directly below an editorial body block (the book-detail about section). Parts are joined with a `  ·  ` separator; each ISBN carries its own inline `ISBN-13` / `ISBN-10` label as a prefix on the value (no eyebrow, no separate metadata table). When both ISBNs are known the modern one (`ISBN-13`) leads; either is rendered alone when only one is known. The line is suppressed when none of the three fields is known so the about block snaps straight into whatever follows. Reach for this pattern when a screen needs to name a physical-edition fact in passing without earning a section header or its own card; do not promote it to a labelled metadata table.
- **External-links strip.** A "Find it" `SectionLabel` (full 32×4 accent bar + eyebrow) followed by a flat `Row` of icon-only `IconButton`s that hand off to off-app destinations. Used on book detail under the about / colophon stack to route the reader to a print/library lookup for the currently-selected edition — Bookshop.org, Amazon, OpenLibrary, all keyed off the edition's ISBN as a search query (prefer `edition.isbn13`, fall back to `edition.isbn10`). Icons follow the existing 960vp Material Symbols vocabulary (`ic_storefront`, `ic_shopping_bag`, `ic_library_books`) tinted `onSurfaceVariant` so the row reads as utility chrome, not as a CTA. The handoff itself goes through a `UiEvent` (the strip dispatches an `OnExternalLinkClickAction` carrying the URL; the screen's top-level `Content()` collects the resulting `OpenExternalLinkEvent` and invokes `LocalUriHandler.openUri` there) — never call `LocalUriHandler` from inside the strip, or any other leaf composable. The entire strip — eyebrow included — is suppressed when the current edition has neither ISBN, since every button would be dead; do not render the eyebrow above an empty row. Each `IconButton` carries a verbose `contentDescription` ("Find on Bookshop.org", etc.) because the brand identity isn't carried by the glyph. Reach for this pattern wherever a detail surface needs to launch the reader into a small, fixed set of off-app lookups for the entity in view; do not stretch it into a generic "share/open in…" sheet — for that, reach for the share-sheet pattern.
- **Adaptive empty state.** When a root surface is empty, surface the next-best content rather than a static "nothing here" panel. The empty Reading screen demonstrates the rule: if Want-to-Read has entries, render the top three as a "Pick up next" tile row (96dp covers + title only); else, render a single "Trending now" tile that links into book detail. Pair with the existing empty-state quote glyph + headline (§5 editorial quote, empty-state variant); do not stack three carousels — the empty state is a moment of orientation, not a discovery surface.
- **Bulk-select mode.** Long-press a cover on a built-in shelf tab (All / Want-to-Read / Currently Reading / Read) to enter selection mode — **on desktop, where long-press is invisible to a pointer, entry is via right-click → "Select" or Ctrl/Cmd-click, with Shift-click range select (§2.5 desktop selection); the desktop right-click menu also exposes the per-book operations directly.** — fire `Haptics.threshold()` at activation, `Haptics.select()` on every subsequent toggle, `Haptics.commit()` when the user applies a bulk action. The page header swaps to a selection bar: a leading `ic_close` exit button, an editorial `titleMedium` "N selected" count, and trailing icon actions (`ic_bookmark` opens a dropdown of move-shelf targets; `ic_bookmark_add` opens the shared `ChooseListsBottomSheet` for add-to-list; `ic_delete` opens a confirmation `AlertDialog`). The shelf-tab strip, search field, filter chip row, and Read-tab year row all hide while in selection mode; pager swipes are disabled so scope can't drift silently. Back press, the close button, switching tabs, and deselecting the last book all exit. Per-cover anatomy: a 24dp circular badge sits at the top-end of the cover (filled `primary` with `ic_check` for selected, translucent `surface` ring for unselected), and unselected covers dim to ~0.55 alpha so the selection state reads even on dense grids. For `LIST_COMPACT` rows the badge moves to a leading position before the title. The add-to-list sheet uses the same surface as book detail, generalised to accept a `Set<bookId>` and to render tristate membership per list (none / partial / all — tapping commits toward the larger end, matching the standard tristate-checkbox UX); after a successful toggle the surface stays in selection mode so consecutive adds across multiple lists feel like one operation. Custom-list tabs (which render editions rather than books) do not opt into selection — long-press is a no-op there. Reach for this pattern whenever a root list surface needs N-target operations; do not invent a per-screen variant.
- **Rearrange mode.** A transient editing mode that gates drag-to-reorder behind an explicit opt-in, so a positional sort (MANUAL on a built-in shelf, ORDER on a ranked custom list) renders *display-only* by default — normal scroll/tap/long-press, no drag handles — and the order can't be nudged while browsing. Entered and exited from a **drag-handle icon-button** in the view-control strip's trailing cluster (beside the layout button): it appears only when the current tab is on a positional sort with ≥2 visible items, reads as plain chrome (like the layout button) when idle and fills to `secondaryContainer`/`onSecondaryContainer` while rearranging — the one button is both the entry and the `Done` exit. (It is a trailing icon, not a fourth leading pill, because a labelled pill overflows Sort + Filter + Layout on narrow screens.) Entering reveals the per-card drag handles (see the two "Drag-to-reorder … grid variant" patterns for handle anatomy and persistence); the mode is **drag-only** — tap-to-open and long-press-to-select are suppressed so the gesture vocabulary stays unambiguous while handles are live. Crucially, entering/leaving the mode must **not** swap the grid for a different composable: the display and reorder states are rendered by the **same** grid node (items only gain a handle and drop their tap targets), because disposing one grid and composing another remounts every cover's image and flashes the screen. Exits on the button (now `Done`), system back, switching tabs, or changing the sort. It is **mutually exclusive with bulk-select** (entering either clears the other), and it is the editing-mode sibling of "Bulk-select mode" above — reach for it whenever a surface offers an in-place reorder that would otherwise let casual scrolling perturb the order; do not leave always-live drag handles on a freely-scrolling grid.
- **Drag-to-reorder list.** A tonal-grouped `Column` (surfaceContainer / RoundedCornerShape(20dp)) of rows, each prefixed with a leading `ic_drag_handle` glyph in `onSurfaceVariant`. Pressing the handle picks the row up immediately (no long-press; the handle *is* the affordance) — fire `Haptics.lift()` (§2.5), tint the handle `primary`, and translate the row vertically with the drag via `graphicsLayer { translationY }`. The other rows stay where they are during the drag; the row does **not** snap into intermediate slots while the finger is down. On release, compute the target slot from the cumulative offset (walking neighbouring row heights until the offset is consumed past the midpoint of each), commit the new order, and fire `Haptics.drop()`. Gesture wiring uses `Modifier.draggable(orientation = Vertical, startDragImmediately = true)` so it composes with a vertically-scrolling parent without fighting it. Long-press *outside* the handle (e.g. on a tab pill in the Library strip) is the canonical shortcut into the reorder screen — fire `Haptics.threshold()` and route to the canonical Settings entry rather than spawning an inline reorder mode. Used today for the Library tabs list under Settings → Library.
- **Drag-to-reorder shelf (grid variant — built-in shelves, MANUAL).** Used on the built-in Library shelves (Want-to-Read, Currently Reading, Read) when the tab's sort mode is `MANUAL`. MANUAL is exposed in the sort dropdown only for those three shelves — the All tab and Did Not Finish suppress it; custom-list tabs use the separate `ORDER` mode below — and the dropdown hides its direction arrow because the stored position itself is the order. **Selecting MANUAL is display-only:** the saved order renders with normal scroll, tap-to-open, and long-press-to-select intact and *no drag handles*, so the order can't be nudged while browsing. Dragging is gated behind an explicit **Rearrange mode** (see "Rearrange mode" below), entered from the control-strip Rearrange icon-button. Only while rearranging does each card gain a grab affordance overlaid at its top-end: a circular `surfaceContainerHigh`-tinted pill (~28dp, 4dp padding, alpha 0.9, `onSurfaceVariant` content) wrapping an `ic_drag_handle` glyph, wired via `Modifier.draggableHandle(...)` from the `sh.calvin.reorderable` library. Pressing the handle fires `Haptics.lift()`, the reorder library snaps neighbouring cards into intermediate slots during the drag, and release fires `Haptics.drop()`. Rearrange mode is drag-only — tapping a cover does not navigate and long-press does not enter bulk-select, so the gesture vocabulary stays unambiguous while the handle is live (the long-press → bulk-select shortcut lives on the display-only path instead). Rearrange and bulk-select are mutually exclusive: entering one clears the other. Persistence is local-only and **prefix-scoped**: on drop, only positions `0..maxTouchedIndex` are written, where `maxTouchedIndex` is the deepest visual index any move spanned. Books beyond that depth retain whatever state they had (positioned or unsorted), so a shallow drag at the top of the shelf doesn't pin books the user never touched, and newcomers fetched from the API surface at the top of the unsorted region — immediately below the pinned prefix — rather than at the very bottom. Reach for this pattern wherever a grid surface needs an in-place reorder that coexists with a separate sort dimension and with bulk-select.
- **Reading-session peek bar.** While a reading session is running, a persistent live-timer bar (`SessionPeekBar`, §4) sits directly above the bottom navigation — between the tab content and the nav, in both the docked and floating bar styles — and slides in when a session starts, out when it ends. It is the always-glanceable in-app counterpart to the lock-screen notification — a **plain, persistent ongoing notification** (`BigPictureStyle` edition cover, running chronometer, pause/resume + stop + an inline "update page" reply), hosted by `ReadingSessionService` as a foreground service and kept persistent — since Android 14 ignores `setOngoing` for FGS notifications, a `deleteIntent` re-posts it if the user swipes it away, so it returns and is removed only when the session ends. It is deliberately **not** a media/`MediaSession` notification: that was tried and abandoned because a real audio app (Spotify) wins the single media slot and overwrites it, and because a media session drags in the speaker-output chip and media-button capture. A plain notification always shows independently, touches no audio routing, and never competes for media controls. All three surfaces (peek bar, lock screen, Focus Mode) read and drive the one app-scoped `ActiveSessionController`: same book, same running timer, same pause/resume + stop controls. Tapping it opens Focus Mode. Mount it once at the app shell; never reserve layout space for it when idle (it animates from zero height), and never let a screen render its own session timer — if a surface needs to show "you're reading this now", it reads the controller.
- **Focus Mode.** A distraction-free full-screen reading surface for the active session, pushed over the bottom-bar shell (so the peek bar and nav recede). It is an **editorial hero on the page `surface`** (§3.3), not a dark scrim — a centred column reading top-to-bottom: a `NOW READING` eyebrow (primary), the book cover (subtle radius + shadow, §2.3), the title in `display` (italic, on-surface) over a `By …` byline in `body` (on-surface-variant), then the running timer as a **hero stat** (§5) — an eyebrow label (`READING TIME`, or `PAUSED` in on-surface-variant) above the `statHero` numeral (a formatted `H:MM:SS` string driven by a one-second `LaunchedEffect`, dimmed to on-surface-variant while paused; `AnimatedStatNumber` is for live integers, not a composite time string, so it does not apply here). Below sits the editable page as an **editable hero stat** (`HeroStatNumberField` + `EditorialSuffix` "of N pages" + a progress bar — the same treatment as the progress sheet's page tab; it commits the new page on focus loss through the same `RecordBookProgressUseCase` the reading screen uses, and falls back to a read-only "% complete" for books without a page count), then a pause/resume (`FILLED`) + stop (`OUTLINED`) `RhaydusButton` row. All copy uses editorial roles on the page surface so it stays legible — never dark-on-dark. It owns no domain state beyond a transient page-input buffer, so it reads `ActiveSessionController` directly rather than carrying a TOAD ScreenModel, and pops itself the instant no session is active. Reached three ways — the peek-bar tap, the featured-card "Focus mode" button, and the lock-screen notification's content tap (deep-linked through a `singleTop` `MainActivity` into a consumable focus-mode flag the root observes). Reach for this register when a session wants the whole screen; do not build a second full-screen timer.
- **Streak strip.** A compact 21-day reading-activity row sitting in the Reading screen header, directly below the greeting subtitle. Days run **most-recent-first** — today at the left edge, older days trailing right — inside a **horizontally scrolling** `Row` (`Modifier.horizontalScroll`, fixed dot size + `spacedBy` gap) so every dot stays comfortably sized rather than cramming 21 into the viewport and clipping the recent end on narrow phones. A **lit** day (the user read anything that day) is a filled `primary` dot; an **unread** day is a faint track dot (`onSurfaceVariant` at ~0.18 alpha); **today** is a slightly larger dot (filled `primary` when read, or a `primary`-ringed track dot when not) anchored at the scroll origin so it reads as the home position. Orientation is carried by a **static, direction-only caption** beneath the dots ("Most recent first", `eyebrowSmall`/`onSurfaceVariant`) — deliberately *not* a per-end date label, since a scrolling row would make any pinned "Today / 10 May" end-marker drift out of sync with the dot it names. The dot is **binary** — it reflects *that day's own* reading activity, fully decoupled from the current streak run (a gap day simply goes dark while earlier read days stay lit). "Read anything" is sourced from the same Hardcover reading-journal dates the Profile streak uses — never from optional reading sessions, which users may not run. The whole row is one `pressScaleClickable` tap target that fires `Haptics.select()` (§2.5) and opens a transient per-day breakdown `AdaptiveModalSheet` that — like every sheet (§3.5) — opens with `EditorialSectionHeader` (a "Last N days" eyebrow + a "you read N of the last 21 days" headline), then one row per day, most-recent first, each with its dot and a relative `Today`/`Yesterday`/`EEE d MMM` label. It is the interim affordance until the full Reading Activity calendar lands. The strip carries a fixed dot-cell height so dots filling in never reflow it; when no day in the window has activity it is **omitted entirely** (not space-reserved) so a new user never sees a row of dead dots — accept the one-time header grow when the first day is logged. Reach for this pattern when a header needs an at-a-glance binary activity history; do not overload the dot with duration/intensity tiers (that is the calendar's job).
- **Drag-to-reorder custom list (grid variant — ORDER, ranked-gated).** The custom-list counterpart to the MANUAL shelf variant above, with two consequential differences. **(1) Server-owned positions:** the order lives on Hardcover's `list_books.position` column, not in a local-only table. **(2) Gated on the list's `ranked` flag:** the sort dropdown exposes `ORDER` only when `lists.ranked = true`. Unranked custom lists show the four in-memory sorts (Title / Author / Page count / Release date) followed by a single tonal footer item — `✶ Make this list ordered` (`bodyMedium` tinted `primary`, preceded by a `HorizontalDivider`) — that flips `ranked` to true via the `UpdateList` mutation. The flip is optimistic: the local cache toggles immediately, the tab's stored sort auto-switches to `ORDER` so the user lands directly on the reorderable grid, and the server call follows; on failure both are rolled back and a snackbar surfaces ("Couldn't enable manual ordering for "…" — try again."). Like MANUAL, `ORDER` is display-only until the user enters **Rearrange mode** from the control-strip Rearrange icon-button; drag anatomy and haptics then match the MANUAL variant (overlay handle, `lift` on grab, `drop` on release, drag-only with tap-to-open suppressed while the handle is live). Persistence is **range-scoped**, not prefix-scoped: on drop, only positions `[minTouchedIndex, maxTouchedIndex]` are rewritten (clear-then-set in a single GraphQL mutation that mirrors Hardcover web's two-step `update_list_books` + `update_list_books_many` pattern). Books outside the range keep their existing positions, so a swap of two adjacent middle items only touches those two slots on the server, never the rest of the list — matching the web client's semantics so two devices editing the same list don't fight each other. On server failure the optimistic local write stands and the next list refresh reconciles. Reach for this pattern wherever a server-owned ordered collection needs in-place reorder.

## 6. Decision rules

When a new surface is being built, walk this list before reaching for novelty.

- **Need a primary action?** Filled button. One per region.
- **Need an action with a small set of variants?** Split button.
- **Need to edit a single bounded number?** Hero stat field inside a modal sheet.
- **Need to introduce a region of content?** Editorial section (eyebrow + headline).
- **Need to mark a region as elevated relative to its neighbour?** Step the container shade. Do not add a shadow.
- **Need an accent on a piece of text?** Use primary colour on the eyebrow or a leading word. Do not bold or recolour body copy.
- **Need a divider?** First try a vertical gap or a tone change. Reach for a hairline divider only when neither will do.
- **Need a custom font weight, size, or italic toggle?** Pick a different role from the editorial scale instead.
- **Need to show progress?** Wavy progress indicator. Always.
- **Need a modal interaction?** `AdaptiveModalSheet` first (a bottom sheet on compact/medium, a centered editorial panel on expanded — §3.5); full-screen second; a bare `Dialog` only for an overlay too transient to earn the editorial header.
- **Laying out a list or grid on a large window?** Scale columns by the width class (§2.7) and cap the total content width (§3.6) — never stretch a fixed-column layout edge-to-edge. Respect a user-chosen density (e.g. the library grid count); add columns or cap width around it, don't override it.
- **Putting long-form body or a form on a large window?** Centre it at the editorial reading width (`cappedContentWidth`, §3.6). Keep hero and cover media full-bleed.
- **Building a root list surface that opens a detail?** Route the open through the shell's `BookDetailPresenter`, not a direct push — it adapts to the list–detail two-pane on expanded (§5) for free.
